# 新聞模組 — 釘選主題也注入「一般聊天」

> 狀態：**提案，未實作。** 規格外功能（小型行為調整）。
> 提出日：2026-08-03（owner 於 B1 續刀驗收時提出）。
> 相關：`src/main/modules/news/trigger.ts`、`src/main/ipcHandlers.ts`、
> `src/core/news/topicState.ts`、`docs/news-module-design.md`。
>
> **這是行為變更，刻意沒有混進 B1 抽 core 的純重構裡。**

## 現況（不是 bug，是原本的設計）

釘選的新聞主題（`topicState`）只在**兩條路徑**會進 prompt：

| 呼叫點 | 路徑 |
|---|---|
| `ipcHandlers.ts:1144` | 提醒（`Reminder.injectNews`） |
| `ipcHandlers.ts:1633` | 說點什麼（`forceSpeakDirect`） |

兩者都經由 `getNewsInjectionForSpeak()`（`trigger.ts:145`），而該函式全專案只有這兩個呼叫點。

**使用者主動發話（一般聊天）完全不會注入主題。** 那條路徑只有
`getConversationSearchContext()`（對話新聞搜尋，另一個功能、預設關閉、靠觸發詞現抓新聞，
與釘選主題無關）。

`trigger.ts:151` 的原始註解寫的是「有釘住的話題時，**主動發話**一律圍繞它聊」——
這裡的「主動發話」專指角色主動開口，不含角色回應使用者。行為與當初意圖一致。

## Owner 的意見（2026-08-03）

> 一般聊天我覺得如果有釘選新聞主題的話，也應該注入 prompt，
> 不然就失去釘選它的意義了。

具體會遇到的情境：使用者釘了某則新聞當主題，接著自己開口問
「你覺得那件事怎麼樣？」——角色其實**不知道「那件事」是哪件事**，
除非它剛好在先前的對話裡已經講過而還留在上下文內。
釘選這個動作在使用者心裡的語意是「接下來我們聊這個」，
但程式只實作了其中一半（角色主動開口那一半）。

## 實作要點（實作前先讀完這節）

### 1. 一般聊天的注入要「降級」，不能照抄說點什麼那份

說點什麼路徑用的是 `buildTopicDirective()`，那是**主導型指令**——
直接要求角色圍繞該則新聞發言。若一般聊天原封不動套用，
會變成使用者問什麼、角色都硬把話題扯回那則新聞，體感很糟。

一般聊天應改為**背景參考**語氣，大意是「使用者目前釘著這則新聞當話題，
若對話提及可自然接上；沒提到就不必主動帶入」。
措辭沿用既有慣例：**指令用英文省 token，輸出仍強制繁中**（見 CLAUDE.md 新聞模組段）。

`buildTopicContextString()`（純內容，無指令）本身應該可以直接沿用，
要另寫的是一個新的、較弱的 directive。

### 2. Token 成本

主題釘著的期間，**每一輪對話都會多注入一段**。
主題文字含標題＋摘要，量不大，但會持續累加在每一輪。
可接受，但要在 UI 或文件上讓使用者知道「釘著就是會一直帶」。
（既有的「取消主題」入口已經足夠，不必新增開關。）

### 3. 情境模組覆蓋要吃得到

一般聊天路徑已經有
`isModuleEffectivelyEnabled(NEWS_MODULE_ID, ...)` 的計算結果可用，
新的注入必須比照 `weather` / `spotify` / `calendar` 的作法掛在同一個判斷下，
不可繞過——否則「TRPG 情境關掉新聞」會失效。

### 4. Debug 面板

`NewsDebugInfo.mode` 目前有 `'topic' | 'news' | 'survey' | 'none'`。
一般聊天若注入了主題，LogWindow 的新聞 debug 面板應該要看得出來，
否則使用者無從確認有沒有生效。可能需要新增一個 mode 值（例如 `'topic-passive'`）
或在既有結構上加旗標——**這會動到型別，實作時留意 renderer 端有一份手動同步的
`src/renderer/src/modules/news/types.ts`**（見 `docs/multi-device-platform-roadmap.md` §4.4 末段
記載的重複實作問題；若那時已經解掉，這裡就不必兩邊改）。

## 什麼時候做

**不急，但成本很低（估半天內）。** 建議時機：

- **不要**插在 B2（Capacitor ＋ adapter 介面）中間 —— B2 是架構工作，混進行為變更會讓驗收失焦
- 適合在 B2 開工**前**當作一個獨立的小 commit 收掉，或等 B2 告一段落後再回頭做
- 若 renderer 重複型別那件事先解掉了，這件事會更好做（第 4 點只需改一處）

## 已排除的做法

| 做法 | 為何不採用 |
|---|---|
| 一般聊天直接沿用 `buildTopicDirective()` | 角色會不管使用者問什麼都硬扯回那則新聞（見第 1 點） |
| 只在使用者訊息含關鍵字時才注入 | 又要一套觸發詞判斷，`conversationSearch` 已經有一套了，再加一套只會讓行為更難預測 |
| 新增「主題是否影響一般聊天」設定開關 | 違反 §2 目標 4（分層規則）。釘選這個動作的語意本來就該包含「接下來聊這個」，不該再問使用者一次 |
