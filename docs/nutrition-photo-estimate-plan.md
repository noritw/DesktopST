## 0. 一句話

拍一張照 → AI 估出「名稱＋熱量＋蛋白（＋碳水／脂肪／鈉／糖備查）」→ 一鍵存入 → 同時寫進**食物庫**與**今日餐次**；
估錯才進「修改模式」對話式調整再回存，正常路徑**不打字、不看表單**。
> 兩條入口：**即時拍**（§2）與**回家用相簿補記**（§2.5），共用同一套結果卡與回存邏輯；
> 舊食物可**一鍵重估**（§2.11），新舊並排、逐欄選是否覆蓋，預設不動既有值。
> 送出前一律經過**補充說明頁**（§2.7，可留白、手動分槽多份食物）；零食類另有**秤重模式**（§2.8）；
> 份數上限與費用預估由選用模型推導（§2.9）。**整條 AI 路徑可關，預設關**（§2.10）。

## 1. 設計原則（本文件的硬規則）

1. **三步以內完成新食物入帳**：拍照 → 看一眼結果 → 存。中間**不得**插入必填表單、分類選擇、份量輪盤。
2. **預設值必須夠好，讓使用者可以不看**：份量預設 1 份、時間預設現在、餐別由時間推算。全部可事後改。
2b. **送出前一定有一次補充機會**：一個可留白的說明欄，讓 owner 用文字講清楚吃了什麼、多少 —— 文字比讓模型從圖上猜準得多。留白就直接送，不算多一道關卡。
3. **修改是例外路徑**：只有按下「不對」才展開。修改成本可以高一點，但不得污染正常路徑。
4. **AI 只在新食物出現**：拍照後先過本機比對；命中舊食物直接沿用營養（母規格 §3.2 的「庫內禁止 LLM 覆寫」照舊）。
5. **文字優先於影像**：使用者在補充說明裡明講的（品項、份量、吃了幾片），一律優先於模型從圖上推論的結果；圖片只用來補使用者沒講的部分。
6. **有標示就不准猜**：照片裡若有營養成分表，數字一律以標示為準，LLM 只負責讀出來（OCR＋換算），不得用「一般三明治大約…」覆蓋（§2.6）。
7. **絕不主動掃相簿**：只讀使用者當次明確選取的照片。不要求相簿讀取權限、不做背景掃描、不做「你有幾張沒記錄」提示 —— 相簿裡不是只有食物。
7b. **碳水／脂肪／鈉／糖隨手估、不主打**：母規格 §2.1／§80 已定案「醣、脂肪可選存進 FoodItem 備查，
   UI／Widget／報表不主打」；**鈉、糖比照同一原則納入**（owner 2026-08-19：鈉吃多水腫、糖吃多血糖高，
   雖非本期主打指標，但既然要送 AI 辨識，順手記下幾乎零成本）。
   AI 反正要讀營養標示或估算，順手把這四欄一起要，多花的 token 幾乎為零，
   但**不能因此讓結果卡變擁擠**：正常結果卡只顯示 kcal／蛋白，其餘四項存進資料但預設收在「更多」或詳情頁，不佔第一眼視線。
   **與碳水／脂肪的差異**：鈉、糖對 owner 有明確生理意義（水腫、血糖），
   之後若要做「日鈉上限」「日糖上限」提醒，資料已經在，不必再回頭重估——但**這期不做上限與警示 UI**，
   純記錄備查，是否要跟熱量／蛋白一樣升級成「有上限有警示」的一等欄位，留 §9 給 owner 之後拍板。
8. **整個 AI 估算是可關的**：本文件描述的是一條**加值路徑**，不是飲食模組的必經之路。
   關掉之後手打入帳必須完整可用，且 UI 不留任何殘影或推銷（§2.10）。
9. **一次呼叫、一次結果**：不做多輪自動追問；AI 一次回不完整就顯示缺欄位讓使用者點。

## 2. 正常路徑（Happy Path）

### 2.1 四步（含送出前補充）

```
[1] 飲食入口／快覽 → 按「拍照記錄」（相機直接開，不先進中介頁）
        ↓ 拍完或從相簿選（accept 只給 image/*）
[2] 結果卡（3～6 秒內出現）
        燻雞三明治 · 7-11
        約 320 kcal · 蛋白 18 g · 1 份
        [ 存入 ]   [ 不對，我改 ]
        ↓ 按「存入」
[4] 完成：Toast「已記錄 · 今日 1180 / 1800 kcal」，回到快覽／今日列表
```

實際觸控次數：開相機 1、快門 1、**估算 1**、存入 1 —— **4 touch、0 打字**。
（原本設計是 3 touch 直送，但 owner 明確要求送出前能補充說明；那一頁留白直接按「估算」即可，
多的是一次點擊、不是一次填表 —— 換來的是模型不必從圖上猜份量與品項，準確率差很多。）

### 2.2 「存入」到底做了什麼（單一動作、兩筆寫入）

| 情況 | 行為 |
|---|---|
| 比對到既有 `FoodItem`（信心足） | **不新建**：只寫一筆 `MealLog`（foodItemId 沿用、servings 用估的、eatenAt=now）；照片可選附在 MealLog |
| 未命中 → 新食物 | 新建 `FoodItem`（name／brand／flavor／perServing／photoKeys[0]＝這張照片、source=`llm-photo`）＋ 寫一筆 `MealLog` |

兩者都由一顆按鈕完成，UI 不讓使用者選「要不要建食物庫」——**新食物一律進庫**，否則下次還要再估一次（違反母規格「熟食重複記帳趨近零 token」）。

### 2.3 相片命中既有食物的判定（免 LLM 或省 LLM）

順序：

1. **最近清單快捷**：結果卡上方常駐一列「最近吃過」（依 `lastEatenAt`／`useCount`），使用者其實常常在拍照前就能一點命中 → 那條路徑是 **2 touch**，不走 AI。
2. **AI 回傳名稱後比對本機庫**：以 `name` + `aliases` + `brand` 做正規化比對（`core/` 純函式）。
   - 命中唯一 → 結果卡直接顯示庫內營養，並標示「沿用你的紀錄（已記錄 12 次）」；**不採用 AI 的數字**。
   - 命中多筆 → 結果卡下方列出候選（副標＝品牌／口味＋每份 kcal＋上次食用，規則同母規格 §3.2b），點一下即代入，仍是 3 touch。
   - 未命中 → 用 AI 估的數字，新建。

> 不做影像特徵比對／向量檢索。第一期只靠「AI 出名稱 → 文字比對」，成本低且可測。

## 2.5 補記路徑（相簿補登）—— 在外只來得及拍照，回家再記

這是 owner 的**第二種主要情境**，不是邊角案例：外面時間只夠開系統相機按快門，
沒空開 App、沒空打字；回家（或當晚、隔天）才用相簿裡那幾張照片補記錄。

### 2.5.1 設計要點

1. **在外不需要動到 DeST**：用手機原生相機即可。App 不強迫使用者從我們的入口拍照。
2. **時間必須回填成當時**，不是補記當下 —— 否則整份熱量記錄的日期會全錯（見 §2.5.3）。
3. **一次處理多張**：一天可能有 3～4 餐都是這樣拍的，必須批次，不能一張一張重來三步。
4. **不要求使用者記得哪張是哪餐**：靠 EXIF 時間自動歸日、歸餐別。

### 2.5.2 批次補記

```
[1] 飲食入口 → 「從相簿補記」
        ↓ 系統相簿多選（accept 只給 image/*，不列副檔名）
        ↓ 選 3 張 → 確定
[2] 佇列逐張出結果卡（背景已同時送出估算，滑到下一張時通常已算好）
        午餐 · 8/19 12:34（取自照片時間）
        燻雞三明治 · 7-11 · 約 320 kcal · 蛋白 18 g
        [ 存入 ]  [ 不對，我改 ]  [ 跳過這張 ]
        ↓ 每張按一次「存入」
[3] 完成頁：「已補記 3 筆 · 8/19 共 1480 kcal」
```

觸控數：開相簿 1、多選 N、確定 1、每張存入 1 → **N 張 = N + 3 次**，
且**完全不需打字**、不需自己挑日期時間。單張時退化為 3 touch，與正常路徑一致。

> 更快的變體（P3 再評估）：結果卡提供「全部存入」一顆按鈕，
> 只在 `confidence: low` 或比對到多筆候選的那幾張停下來讓人確認 →
> 3 張也可能只要 4 touch。預設**不**開啟全部存入，避免整批錯記難收拾。

### 2.5.3 時間怎麼決定（重要）

優先序，取第一個有值的：

| 來源 | 說明 |
|---|---|
| **EXIF `DateTimeOriginal`** | 主要來源。相簿照片幾乎都有 |
| 檔案 mtime／`File.lastModified` | EXIF 被相簿 App 洗掉時的退路 |
| 使用者手選 | 前兩者都沒有 → 結果卡上的時間顯示為可點的「請確認時間」，**此時才要求互動** |

- 結果卡上永遠**顯示**那個時間（`8/19 12:34`），讓使用者一眼看出是不是補記到對的那天。
- 餐別（早／午／晚／點心）由時間推算，只是顯示用標籤，不影響資料。
- **時區**：以拍照當下的本機時區解讀 EXIF（EXIF 常無時區資訊，第一期就用裝置目前時區，出國補記可能差幾小時 → 由使用者在卡上手改）。
- 跨日補記合法：`MealLog.eatenAt` 寫回當時，今日列表／合計自然歸到正確那一天。

### 2.5.4 已補記過的照片不要重複入帳

批次補記最容易踩的坑是「上次選過的照片這次又選到」。

- 每張照片存檔時記錄一個**內容指紋**（檔案 bytes 的 hash，`core/` 純函式），存在 `MealLog.photoHash`。
- 選圖後先比對指紋：命中 → 該張直接標記「已記錄過（8/19 12:34 燻雞三明治）」，
  **預設跳過**，但保留「仍要再記一筆」按鈕（真的吃了兩份的情況）。
- 指紋只在本機比對，不上傳。

### 2.5.5 佇列與失敗

- 選 N 張後**併發上限 2～3 張**送估算（避免一次打爆 API 與流量），其餘排隊；使用者看第 1 張時第 2、3 張通常已備妥。
- 單張失敗（逾時／解析失敗）→ 該張留在佇列標紅，不擋後面；最後在完成頁列出「2 筆待處理」，可重試或手動輸入。
- 中途離開 App → **佇列要持久化**（存模組資料目錄的暫存區，含已複製的照片與已得到的估算結果），回來可續。這是相簿補記與即時拍照最大的實作差異。
- 使用者按「跳過這張」→ 該照片不入帳、暫存清掉，指紋也不記錄（下次還可以再選）。

### 2.5.6 桌面版

同一條路徑：把幾張照片一次拖進飲食面板 → 走同一個佇列與結果卡。
桌面讀 EXIF 更容易，且「在外拍、回家用電腦補」也是 owner 會用的組合。

## 2.6 一餐多張照片與營養成分表（實際拍法）

owner 的真實拍法不是「一餐一張美照」，第一期就要吃得下這三種：

| 拍法 | 照片組成 | 誰決定營養數字 |
|---|---|---|
| A. 包裝食品完整拍 | 封面／包裝正面 ＋ **營養成分表** ＋ 實際內容物（2～3 張） | **成分表**（正面只用來取名稱／品牌） |
| B. 常吃的包裝食品 | **只有營養成分表**一張 | 成分表；名稱靠比對既有食物庫或標示上的品名 |
| C. 紙袋／包裝紙裹著的即食品 | 一張，食物被紙袋遮住一部分（如三明治、蛋餅、餅類） | 無標示 → LLM 估，但要處理遮蔽（§2.6.4） |

### 2.6.1 多張＝一餐怎麼組：**手動分槽，不自動猜**

owner 決議（2026-08-19）：**不要照時間自動分組。** 由使用者自己把照片放進「第幾份食物」。

補充頁（§2.7）上就是一列可展開的槽：

```
食物 1   [縮圖][縮圖][縮圖]      說明：______   份量 [−] 1 [+]
食物 2   [縮圖][ ＋ ]            說明：______   份量 [−] 1 [+]
食物 3   [ ＋ 加一份食物 ]
```

- 每份食物**最多 3 張**（對應母規格 `FoodItem.photoKeys` 上限，也對應「正面／成分表／內容物」）。
- 加照片的方式：`＋` 開相機或相簿；也可從相簿一次多選後**拖到**各槽（桌面版更好用）。
- **份數上限由模型能力決定**，不是寫死的常數 —— 見 §2.9。
- 每份食物**各自有**自己的說明欄與份量欄；估算時是**一次請求、多份結果**（省 token）。
- 時間仍自動取 EXIF（§2.5.3），但只當每筆 `MealLog` 的 `eatenAt`，**不參與分組**。

### 2.6.1b 多份結果＝可翻頁的卡片，一次回存

```
   ‹  食物 2 / 3  ›
   燻雞三明治 · 7-11
   依營養標示 · 320 kcal · 蛋白 18 g · 1 份
   [ 不對，我改 ]

   ─────────────────────────
   合計 3 筆 · 810 kcal · 蛋白 34 g
   [        全部存入        ]
```

- 左右翻頁逐張確認；**只有一顆「全部存入」**，不是每張各存一次。
- 任何一張按過「不對，我改」→ 改完回到該張卡，合計即時更新。
- 想丟掉其中一份 → 該卡上「不記錄這份」，合計扣掉，其餘照存。
- 全部存入＝一次交易寫入 N 筆 `MealLog`（＋新食物的 `FoodItem`）；中途失敗全部不寫，不留半套。

### 2.6.2 營養成分表是最高優先來源

LLM 輸出改為帶來源標記：

```jsonc
{
  "name": "燻雞三明治",
  "brand": "7-11",
  "nutritionSource": "label",   // label | estimate | label-partial
  "label": {                     // 只有讀到成分表時才有
    "basis": "per100g",         // per100g | perServing | perPackage
    "servingSizeG": 60,
    "servingsPerPackage": 2,
    "kcal": 250,
    "proteinG": 9,
    "carbsG": 27,
    "fatG": 9,
    "sugarG": 8,
    "sodiumMg": 480
  },
  "perServing": { "kcal": 300, "proteinG": 10.8, "carbsG": 32, "fatG": 11, "sugarG": 9, "sodiumMg": 520 },  // 換算後、實際吃下去的一份；碳水/脂肪/糖/鈉皆備查用，不強制精確
  "eatenPortion": 1,             // 這次吃了整包／半包
  "confidence": "high"
}
```

規則：

1. 組內**任一張**讀到成分表 → `nutritionSource: "label"`，`perServing` 必須由 `label` 換算得出，**不得**是模型的經驗值。
2. 換算是**本機純函式**做的，不是叫 LLM 算數：
   `normalizeLabel(label, eatenPortion)` → `{ kcal, proteinG, carbsG, fatG, sugarG, sodiumMg }`（`core/`，可測；碳水／脂肪／糖／鈉缺值時回 `null`，不補假數字）。
   台灣標示常見三種基準都要支援：`每100公克` / `每一份量 X 公克，本包裝含 Y 份` / `每包裝`。
   **模型只負責把表上的字讀成結構化欄位，算術一律本機做** —— 模型算錯的機率遠高於讀錯。
3. 表格數字缺一半（拍糊、被反光蓋掉）→ `label-partial`：讀到的用標示、缺的標成「？」，結果卡把該欄變成待補的可點欄位，仍可直接存（存成 0 或空，不阻擋）。
4. **結果卡要顯示來源徽章**：`依營養標示` / `AI 估算` / `標示不完整`。你一眼就知道這筆數字可不可信 —— 這比多一位小數重要。
5. 存進食物庫時 `FoodItem.source` 記為 `label` 的那些，**日後不再被任何 LLM 路徑覆寫**（比 `llm-photo` 更硬）。

### 2.6.3 只拍成分表（拍法 B）

- 組內沒有正面照 → 名稱來源依序：成分表照片上的**品名文字** → 比對既有食物庫（同品牌＋相近數字）→ 都沒有就用 `未命名（依標示）` 並**在結果卡把名稱欄變成第一個可點的欄位**。
- 命中既有食物時，結果卡顯示「符合你庫裡的『燻雞三明治 · 7-11』（已記錄 12 次）」，一鍵存＝只寫 `MealLog`，數字沿用庫內。
- 若庫內數字與這次讀到的標示**不一致**（廠商改配方／你記錯）→ 卡上顯示兩組數字並提供「更新食物庫為新標示」按鈕，**預設不更新**（守住母規格「庫內禁止 LLM 覆寫」）。

### 2.6.4 紙袋／包裝紙遮住（拍法 C）

沒有標示可讀，只能估，但要估得比「看到麵包就 250 kcal」好：

- prompt 明確告知**食物可能被包裝紙、紙袋、餐盒部分遮住**，要求模型：
  - 只根據**可見部分**推論內容物，看不到的餡料**不要編**（寧可 `confidence: medium`）；
  - 用可見的麵包片數／厚度／相對紙袋的尺寸推**份量**，而不是預設一份；
  - 包裝紙上的**店家標誌／印刷字樣**要拿來當品牌線索（如你這張的包裝紙圖樣）。
- 這類食物多半是**你的常吃品項** → 最有效的其實不是模型變聰明，而是 §2.3 的比對：第一次記完進庫、之後同一家的三明治直接命中沿用，數字永遠一致。
- 結果卡對這類會顯示 `AI 估算` 徽章 ＋ 一行「看到：白吐司、生菜、醬料；紙袋遮住內餡」，讓你能判斷要不要按「不對，我改」。

### 2.6.5 對 §2.2「存入」的影響

一組多張存入時：
- `FoodItem.photoKeys` 依序放 **正面 → 成分表 → 內容物**（母規格上限 3 張，剛好對應）；
- 成分表那張特別重要（日後查證用），若超過 3 張要取捨，**成分表優先保留**；
- `MealLog` 仍只有一筆，`photoHash` 取組內第一張，其餘張的 hash 一併記錄以免重複入帳。

## 2.7 送出前補充說明（送出前的唯一一頁）

owner 決議：**比起讓系統從時間／圖片自動推論，寧可在送出前自己補一句話。**
文字是最高優先線索（§1 原則 5），模型只用圖片補你沒講的部分。

### 2.7.1 版面（一頁、一屏內看完）

```
┌───────────────────────────────────────┐
│  食物 1   [縮圖][縮圖][ ＋ ]             │
│    說明（可留白） ┌──────────────────┐  │
│                  │ 吃了半個便當      │  │
│                  └──────────────────┘  │
│    份量  [ − ]  1  [ ＋ ]   份 ⇄ 克     │
│  ─────────────────────────────────    │
│  食物 2   [縮圖][ ＋ ]                  │
│    說明（可留白） …    份量 [−] 1 [+]    │
│                                       │
│  [ ＋ 加一份食物 ]        （已 2 / 上限 5）│
│                                       │
│  時間  8/19 12:34  (可點改)             │
│  ─────────────────────────────────    │
│  模型  gpt-4o-mini · 預估 NT$0.12       │  ← §2.9，可點切換
│         [      估  算      ]           │
└───────────────────────────────────────┘
```

- 每份食物一組（說明＋份量），彼此獨立。
- 說明欄**永遠可留白**，直接按「估算」＝走純影像判斷（等同原本設計）。
- 欄位不做必填、不做下拉選單、不做標籤按鈕 —— 打字或不打字，兩種都順。
- 說明欄可記住「常用語」？→ **不做**（會變成另一種選單，違反 owner 習慣）。

### 2.7.2 文字怎麼餵給模型

補充說明原封不動放進 prompt，並明確指示：

> 使用者的文字說明為**最高優先**。文字有講到的品項與份量，直接採用，不得用圖片推論覆蓋；
> 文字未提到的部分才從圖片判斷。若文字與圖片明顯矛盾，以文字為準，並在 `note` 說明差異。

輸出多一個欄位讓你看得出模型有沒有聽話：

多份食物時，回應是**陣列**，順序必須對齊送出的槽（`slot: 1..N`），
少回或多回都以 `slot` 對齊、缺的那份標為失敗而不是整批作廢：

```jsonc
[{ "slot": 1, "name": "…", "appliedNote": true,
   "noteConflict": "圖中看似整個便當，依說明以半份計" }]   // 無矛盾則 null
```

結果卡若 `noteConflict` 非空，把它顯示成一行小字 —— 這比信心分數有用得多。

### 2.7.3 份量欄（owner 指定樣式）

**不做一排快捷按鈕。** 只有一個數字欄，預設 `1`，兩側 `−` / `＋`。

- 級距（按 `−`／`＋` 走這個序列）：
  `1/3 → 1/2 → 1 → 2 → 3 → … → 10`
  （往下最小到 `1/3`，往上最大到 `10`；到底不再變化）
- **數字本身可點，直接手打**任意值（`0.4`、`1.5`、`0.75` 都行），不受上面級距限制。
- 顯示用分數（`1/2`），存進 `MealLog.servings` 是小數（`0.5`）；`core/` 提供
  `stepServings(current, direction)` 與 `formatServings(value)` 兩個純函式，桌面手機共用。
- 補充說明裡若已寫了份量（「吃一半」），模型回的 `eatenPortion` 會**回填**到這個欄位，
  結果卡上再讓你確認一次 —— 兩邊不打架，以你打的字為準。

### 2.7.4 對補記路徑（§2.5）的影響

批次補記時，每一組照片各自進入自己的補充頁：
- 佇列裡逐組出現 → 補充（可全部留白）→ 估算 → 結果卡存入。
- 想快一點：補充頁右上有「全部略過補充，直接估算」，把佇列裡剩下的組都用留白送出。
  這是**你主動按的**，不是預設行為。

## 2.8 秤重模式（零食類的準確路徑）

owner 的實際做法：拿一小片餅乾／一片海苔出來**秤重**，再拍營養成分表，讓系統算。
這條路徑比任何影像估算都準，**要當成一等公民做，不是進階功能**。

### 2.8.1 流程

```
[1] 拍營養成分表（或從相簿選）
[2] 補充頁 → 份量欄旁邊切到「秤重」→ 輸入 12 (g)
        說明欄可留白
[3] 結果卡：海苔 · 12 g · 依營養標示 · 68 kcal · 蛋白 2.4 g（碳水／脂肪／糖／鈉同時存入，收在詳情——海苔常見鈉偏高，這正是 owner 想備查的情境） → 存入
```

仍是 4 touch ＋ 打一個數字。

### 2.8.2 份量欄的兩種模式

同一個位置，一個小切換（`份` ⇄ `克`）：

| 模式 | 輸入 | 算法 |
|---|---|---|
| `份` | 1 / 1/2 / … | `perServing × servings`（§2.6.2），四欄都換算 |
| `克` | 直接打克數 | 由標示的 `每100公克` 基準換算：`kcal = label.kcal ÷ 100 × grams`，`carbsG`／`fatG`／`sugarG`／`sodiumMg` 同法，缺值不補 |

- 標示只給「每一份量 X 公克」而沒給每 100 公克 → 本機自行推 `每100公克`（`label.kcal ÷ X × 100`），再算。
- 標示連份量克數都沒有（罕見）→ 秤重模式停用並提示「此標示無克數基準，請用份數」。
- 換算一律 `core/`：`nutritionFromGrams(label, grams)`，含三種標示基準的單元測試。
- `MealLog` 存 `amountMode: 'servings' | 'grams'` ＋ `grams?`，兩種都能還原、都能重算。

### 2.8.3 秤重值會被記住

同一個 `FoodItem` 下次再記，份量欄預設帶出**上次用的模式與數值**（海苔上次 12 g → 這次預設 12 g），
可直接改。這讓「常吃的零食」第二次之後幾乎零輸入，且數字永遠一致。

## 2.9 模型能力與費用（自備 Key／本地模型的必要處理）

owner 自備 API Key，也可能接本地模型 —— **「一次能傳幾張圖」和「這一次要花多少錢」都不是常數**，
所以份數上限與費用都必須由「目前選用的模型」推導，而不是寫死。

### 2.9.1 模型能力表（本機、可編）

模組資料目錄放一份 `model-capabilities.json`，內建常見模型的預設值，**使用者可自行增修**
（接本地模型或新模型時不必等作者更新）：

```jsonc
{
  "id": "gpt-4o-mini",
  "vision": true,
  "maxImagesPerRequest": 10,     // 決定「最多幾份食物」
  "maxImageEdgePx": 1568,        // 送出前壓縮的上限
  "pricing": {                    // 缺省則不顯示金額，只顯示張數
    "currency": "USD",
    "inputPerMTok": null,        // 由使用者填或內建預設
    "outputPerMTok": null,
    "imageTokensFormula": "tiles" // tiles | fixed | unknown
  }
}
```

- **未知模型**（使用者自填的本地模型 / 沒列在表裡）：`maxImagesPerRequest` 預設保守值 **3**（owner 拍板 2026-08-19：
  「3 份應該行，不行就多做幾次」——**寧可保守、多送一次，也不要送出去才被模型退件**），
  `pricing` 留空 → UI 顯示「本地模型 · 不計費」或「未知模型 · 費用未知」，**不阻擋使用**。
- 本地模型（Ollama 等）：費用一律顯示 **「本機執行 · 無 API 費用」**。

### 2.9.2 份數上限怎麼算

```
可加的食物份數上限 = floor(maxImagesPerRequest ÷ 每份最多張數(3))
                      再取 min(該值, 硬上限 8)
```

- 例：`maxImagesPerRequest: 10` → 上限 3 份（10÷3）。
- 補充頁右下常駐顯示 `已 2 / 上限 3`；到達上限時 `＋ 加一份食物` 變灰，
  並提示「目前模型一次最多 3 份，可到設定換模型」，**點提示直接跳設定**。
- 若你實際只放了 1～2 張／份，上限可放寬（用**實際已放的張數**動態算，不是用最壞情況）：
  `還能加一份 ⟺ 目前總張數 + 1 ≤ maxImagesPerRequest`。
- 超過上限時的替代路徑：**自動拆成多次請求**？→ **不做**（費用與失敗處理都變複雜）。
  改為請使用者分兩批記錄，或換模型。

### 2.9.3 費用預估（估算按鈕上方那行）

估算前顯示一行，讓你在按下去之前就能決定要不要換模型：

```
模型  gpt-4o-mini · 3 張圖 · 預估 USD $0.0041（估）   ▸切換
```

**幣別一律顯示模型／供應商的原幣別，且必須把幣別標示清楚**（owner 拍板 2026-08-19）：

- 估法：`(圖片 token 估值 + prompt token 估值) × 單價 + 預估輸出 token × 單價`。
  圖片 token 依模型的 `imageTokensFormula` 由**本機純函式**算（`estimateRequestCost()`，`core/`）。
- **不做幣別換算、不抓匯率、不顯示台幣**。單價表填什麼幣別就顯示什麼幣別，少一個出錯與維護的地方。
- 幣別以 **ISO 代碼**顯示（`USD` / `JPY` / `TWD`），**不單獨使用 `$` 這種有歧義的符號**；
  要用符號也必須連著代碼寫（`USD $0.0041`）。金額後綴「（估）」字樣，避免被當成實際帳單。
- 小額不要被四捨五入成 0：金額 < 0.01 時改用更多位數（如 `USD $0.0041`）或顯示 `< USD $0.01`，
  **絕不顯示 `$0.00`** —— 那會讓人誤以為免費。
- 單價表（`model-capabilities.json`）的每個 `pricing` 都**必須帶 `currency`**；缺 `currency` 一律視同缺價，
  顯示 `費用未知`，不猜是美金。
- 費用無法估（未知模型／缺單價／缺幣別）→ 顯示 `費用未知`，不擋操作。
- 同理，設定頁的「本月飲食估算花費」若跨了不同幣別的模型，**分幣別各列一行**，不合計成單一數字。
- 「▸切換」一鍵開模組的模型選單（`nutrition.llm`），切完回到補充頁，**照片與說明都還在**。
- 事後查帳：完成頁與 `MealLog` 可選記下 `estimatedCostMinor` 與實際回傳的 token 用量，
  設定內提供「本月飲食估算花費」一行 —— **只做一行數字**，不做圖表。

### 2.9.4 送出前的相容性檢查

按「估算」時本機先擋掉必然失敗的組合，不要浪費一次請求：

| 檢查 | 行為 |
|---|---|
| 模型 `vision: false` | 直接提示換模型，附「▸切換」 |
| 張數 > `maxImagesPerRequest` | 提示要減幾張（正常情況 UI 已擋住） |
| 未設 API Key 且非本地模型 | 提示去填 Key；照片與說明保留不丟 |
| 單張壓縮後仍超過模型限制 | 自動再壓一階；成分表那張優先保住解析度（§3.1） |

## 2.10 AI 估算開關（整條路徑可關）

owner 決議（2026-08-19）：**AI 拍照估算要有獨立開關。**
理由很實際 —— 使用者完全可以在自己平常用的 AI 那邊算好，再回來手打；
在 DeST 裡算是**要另外付錢**的。這條路徑必須是「想用才開」，不是預設綁上去的成本。

### 2.10.1 開關長怎樣

- 設定位置：飲食模組設定 → `AI 拍照估算`，**預設關**（與母規格「模組預設關、進階不擠第一層」一致）。
- 這是**第三個層級**的開關，與母規格既有的兩層並存：

| 層 | 開關 | 預設 |
|---|---|---|
| 1 | 飲食模組本身 `desktopst.nutrition` | 關 |
| 2 | Health 讀／寫 | 關 |
| 3 | **AI 拍照估算**（本文件） | **關** |

- 開啟時同一頁就能設 `nutrition.llm`（模型、Key、單價表），**不必跑到別的設定頁**——
  這兩件事使用者是同時在想的。
- 開啟前顯示一行老實話：「會使用你自己的 API Key 呼叫模型，**每次估算都會產生費用**（本地模型除外）。」
  不加感嘆號、不推銷。

### 2.10.2 關掉之後（必須完整可用，不是降級版）

**UI 完全移除，不留殘影：**

- 首屏的「拍照記錄」「從相簿補記」按鈕、今日列表的相機 FAB → **隱藏**，不是變灰。
- 不出現任何「開啟 AI 估算更方便」之類的提示、紅點、引導 —— 一次都不要。
- 桌面版拖曳圖片進飲食面板 → 不觸發估算；照片改為**單純附加到食物庫照片**（見下）。

**手打路徑必須自成一套（本來就在母規格裡，這裡只是確認它不依賴 AI）：**

| 需求 | 關掉 AI 後怎麼做 |
|---|---|
| 記已知食物 | 關鍵字對庫（母規格 §3.2 主路徑）→ 選候選 → 份量 → 存。本來就不用 LLM |
| 記新食物 | 手建 `FoodItem`：名稱、品牌、每份 kcal／蛋白（碳水／脂肪／糖／鈉選填，收摺疊區），照片可選 → 直接入帳 |
| 照片還想留 | 手建／編輯食物時仍可從相機或相簿**加照片**（1～3 張），只是**沒有任何辨識**，純存檔 |
| 秤重（§2.8） | **保留可用**：份／克切換與 `nutritionFromGrams` 都是本機純函式，標示數字改由使用者手打 |
| 份量欄（§2.7.3） | **保留**，與 AI 無關 |

> 換句話說：`core/` 裡跟 AI 無關的計算（換算、比對、聚合、份量級距）**一律不得**寫在估算流程內部，
> 必須是獨立純函式，關掉 AI 後照常被手打路徑呼叫。這條在實作時最容易違反，Code Review 要特別看。

### 2.10.3 從別處算好、貼回來（關掉 AI 時的順手做法）

owner 提到的實際情境：在自己常用的 AI 那邊算完再回來輸入。
不做任何 API 串接，只做一件小事降低摩擦：

- 手建食物的表單支援**貼上一段文字自動填欄位**（例如從別的 AI 複製來的「熱量 320 大卡，蛋白質 18 克」）。
- 解析是**本機正則／純函式**（`parsePastedNutrition(text)`，`core/`），**不呼叫任何模型**，
  解析不出來就當沒事、讓使用者照常手打，不跳錯誤。
- 支援常見寫法：`320 kcal`／`320 大卡`／`熱量 320`／`蛋白質 18g`／`蛋白 18 公克`／`碳水 34g`／`脂肪 12 公克`／`糖 5g`／`鈉 610mg`（後四者選填，抓不到不影響其餘欄位照填）。
- 這功能在 AI 開關**開或關都在**（它本來就跟 AI 無關）。

### 2.10.4 資料層面

- 已經用 AI 記過的資料，關掉開關後**照常保留、照常顯示**（`source: llm-photo` 的食物不會消失）。
- 關掉時不刪照片、不刪 `labelRaw`、不動任何既有紀錄。
- 重新開啟 → 一切照舊，不需重設模型。

## 2.11 舊食物一鍵重估（補打回去的營養資料）

owner 的實際情境：食物庫裡不少項目是早期只手打了熱量／蛋白（甚至更早期只有熱量）建的，
沒有照片、沒有碳水脂肪糖鈉。**不必逐筆重建**，在食物詳情頁提供一鍵重估。

### 2.11.1 入口與前提

- 位置：`FoodItem` 詳情頁一顆「重新估算」按鈕。
- 前提照 §2.10 受同一顆 AI 開關管控：開關關閉時這顆按鈕**不出現**。
- 需要照片才能估：
  - 該食物已有 `photoKeys` → 直接用現有照片重估，**不必重拍**。
  - 沒有照片 → 按下後引導去拍一張／從相簿選一張，等同 §2 正常路徑但目標換成「更新既有食物」而非「新建」。
- 進 §2.7 補充頁的方式跟平常一樣（可留白、可打字說明），**份量欄鎖成 1 份**
  （重估的是 `FoodItem.perServing` 這個「每份」定義本身，不是某一次吃的量，跟 §2.6.1 記餐次不同意義，避免混淆）。

### 2.11.2 結果卡：新舊並排，逐欄自己選

這是與 §4「不對，我改」最大的不同 —— 重估**預設不覆蓋**，而是新舊並排讓你逐欄勾：

```
   重新估算結果 —— 燻雞三明治 · 7-11

              目前庫內          AI 這次估的
   熱量        —（未填）         320 kcal      [ 用新的 ]
   蛋白        —（未填）         18 g          [ 用新的 ]
   碳水        —               34 g          [ 用新的 ]
   脂肪        —               12 g          [ 用新的 ]
   糖          —               5 g           [ 用新的 ]
   鈉          —               610 mg        [ 用新的 ]

   [ 全部套用新值 ]   [ 只補空白欄 ]   [ 取消，不覆蓋 ]
```

- 每一欄獨立一顆勾選／切換，預設狀態＝**維持目前庫內值**（若原本是空的，AI 這次的值會**預先勾選**，
  因為「補一個從沒有過的數字」風險遠低於「覆蓋你已經確認過的數字」）。
- 三顆捷徑鈕：
  - **全部套用新值**：整批覆蓋，給「這筆本來就是隨便打的，直接信 AI 這次」的情境。
  - **只補空白欄**：只填目前是 `null`／未填的欄位，**已有值的欄位一律不動**——這是最常用的情境
    （owner 描述的「之前可能只有輸入熱量蛋白質」正是這個：碳水脂肪糖鈉是空的，補上去；
    熱量蛋白質已經有人手動確認過，不要因為 AI 這次估出不同數字就蓋掉）。
  - **取消，不覆蓋**：整份丟棄，`FoodItem` 完全不變。
- 名稱／品牌／口味**不在這個表裡**——重估只動營養數字，不會順便把你已經取好的名字換掉。
  改名走既有的食物庫編輯，兩件事分開做。

### 2.11.3 寫回規則

- 套用後 `FoodItem.source` 更新為 `llm-photo-edited`（表示「經過 AI 重估、使用者確認過」，
  與純粹拍照新建的 `llm-photo` 區分），`updatedAt` 更新。
- 若重估時附了新照片，依 §2.6.5 規則補進 `photoKeys`（成分表優先保留，上限 3 張）。
- 這筆重估的來源與差異可選記一筆到 `FoodItem` 的變更歷程（若母規格日後有變更記錄機制就掛上去；
  **本期不強求**，沒有就算了，不為了這個另建一套歷史記錄）。
- 重估**不影響**已經記錄過的舊 `MealLog`——過去吃的那幾筆熱量還是照舊，只有以後用這個 `FoodItem`
  記錄新的一餐時才會用新數字。這跟母規格「同一 `foodItemId` 的多筆餐次共用同一份食物資料，
  改主檔後全部一起變」的既有行為一致，此處單純提醒：**歷史餐次的熱量本來就會跟著變**，
  這是既有設計，不是本功能新增的風險，但值得在按鈕旁提示一行：
  「更新後，過去用這份食物記錄的餐次熱量也會一併改變」。

### 2.11.4 批次重估（可選，晚一點做）

食物庫可能有幾十筆舊資料都缺欄位。第一期只做逐筆入口即可，
批次「重估所有缺碳水/脂肪/糖/鈉的食物」排入 P5 之後視需求再做——
批次意味著一次送出多筆 LLM 請求，要重新套用 §2.9 的份數上限與費用預估，值得另外評估，不與本期綁在一起。

## 3. AI 呼叫規格

### 3.1 輸入

- **1～N 份食物**、每份 1～3 張壓縮後照片，同一次請求（份數上限見 §2.9.2）。每張標明所屬 `slot`。長邊上限約 1024px、JPEG q≈0.7。
  **例外**：被判定為營養成分表的那張用較高解析度（長邊 1568px 以上）送出，小字才讀得準；壓太狠會讀錯數字。
- **補充說明文字**（§2.7，可空）；有值時在 prompt 中標記為最高優先線索
- 使用者已填的份量／克數（模型不需再猜份量，只需辨識品項與每份營養）
- 指示模型：**若任一張是營養成分表，必須逐欄讀出並填 `label`，不得改用經驗值**；食物可能被包裝紙遮蔽（§2.6.4）；
  **同時附帶估碳水、脂肪、糖、鈉**（成分表有就讀、沒有就依食物常識粗估，抓不到就留空，不強求精確——這四欄是備查用途；
  台灣標示的「鈉」欄位單位固定是毫克 `mg`，讀取時不要跟公克搞混）
- 本機提示：使用者最近／最常吃的 **食物名稱清單（僅名稱，20～40 筆）**，讓模型優先吐出既有名稱以提高命中率。**不送**營養數字、不送體重／上限等個資。

### 3.2 輸出（強制 JSON）

> 完整欄位（含 `label` / `nutritionSource`）見 §2.6.2；以下為無標示時的最小形狀。

```jsonc
{
  "name": "燻雞三明治",
  "brand": "7-11",          // 不確定則 null
  "flavor": null,
  "servings": 1,            // 照片中看到的份數
  "perServing": { "kcal": 320, "proteinG": 18, "carbsG": 34, "fatG": 12, "sugarG": 5, "sodiumMg": 610 },
  "confidence": "high",     // high | medium | low
  "appliedNote": true,      // 是否採用了使用者的補充說明（§2.7.2）
  "noteConflict": null,     // 文字與圖片矛盾時的一句說明
  "note": "三明治，內含雞肉與生菜"   // 一句話，給使用者判斷是否辨識錯
}
```

- 解析失敗／缺欄位 → 不報錯畫面，改顯示「只認出：___，請補熱量」的最小補填卡（仍可一鍵存）。
- `confidence: low` → 結果卡把數字改成**可點的**灰字並提示「不太確定，點數字可改」，但**仍允許直接存**（使用者的容忍度比正確率重要，之後隨時可改）。

### 3.3 模型與設定

- 走母規格 §3.4：`nutrition.llm` 獨立設定，預設挑便宜的 vision 模型，與角色主模型分開。
- 逾時 12 秒；失敗給「重試 / 手動輸入 / 取消」三顆。重試不重新壓縮照片。

## 4. 例外路徑：「不對，我改」

按下後才展開，分兩種修法，同一張卡上切換：

### 4.1 快改（多數情況）

結果卡就地變成可編輯：名稱、品牌、kcal、蛋白、份量、時間。碳水／脂肪／糖／鈉收在「更多欄位」展開列，不擠進主要編輯區。
改完按「存入」，寫入時 `source` 標記為 `llm-photo-edited`（之後可統計 AI 準確度）。

### 4.2 對話式修（辨識完全錯／要重估）

一個輸入框：「這是滷雞腿便當，不是雞排飯」→ 帶著**原照片＋原結果＋這句話**再呼叫一次，回新的結果卡。
- 最多允許連續 3 次（避免無限燒 token），超過提示改用快改。
- 每次都是完整重估，不做增量 patch（實作簡單、結果可預期）。

### 4.3 回存規則

| 情境 | 行為 |
|---|---|
| 新食物、改過 | 建立 `FoodItem` 用**改後**的值 |
| 命中舊食物、只是這次份量不同 | **只改 `MealLog.servings`**，不動 `FoodItem` |
| 命中舊食物、但發現主檔數字本來就錯 | 需在卡上明確按「同時更新食物庫」才覆寫 `FoodItem`（預設不勾）——守住母規格「庫內禁止 LLM 覆寫」 |
| 其實是不同食物被比對錯 | 提供「另存為新食物」（母規格 §3.2b 已有此操作，共用同一段邏輯） |

## 6. 資料與檔案落點

沿用母規格 §4，不新增實體。本模組新增／使用的欄位：

- `FoodItem.perServing` 沿用母規格擴充欄位 `{ kcal, proteinG, carbsG?, fatG?, sugarG?, sodiumMg? }`：後四者為**選填**，AI 路徑估得到就存，估不到留空，**不得補假數字**；桌面／手機 UI 皆不主打，僅詳情頁與匯出可見（母規格 §2.1；鈉／糖為 owner 2026-08-19 追加，理由見 §1 原則 7b）
- `FoodItem.source`：`manual` | `label` | `llm-photo` | `llm-photo-edited`（`label` 最硬，不被任何 LLM 路徑覆寫）
- `MealLog.amountMode`：`servings` | `grams`；`grams?`（秤重模式，§2.8）
- `MealLog.note?`：送出前的補充說明原文（保留，方便日後回頭看當時吃了什麼）
- `MealLog.estimatedCostMinor?` / `tokenUsage?`：該次估算的預估與實際用量（§2.9.3，可關）
- 模組 settings 增 `nutrition.photoEstimate.enabled`（預設 `false`，§2.10）
- `model-capabilities.json`：模型能力與單價表，放模組資料目錄，**使用者可編**（§2.9.1）
- `FoodItem.lastAmount?`：上次使用的模式與數值，下次預設帶出（§2.8.3）
- `FoodItem.labelRaw?`：讀到的原始標示欄位（basis／每份克數／每包份數），供日後查證與重算
- `FoodItem.photoKeys[0]`：拍照建立時自動填入這張照片
- `MealLog.photoKey?`：當次照片（與食物庫照片不同張時才存，避免重複佔空間）
- `MealLog.photoHash?` / `photoHashes[]`：照片內容指紋（一組多張時全記），用於補記時避免重複入帳（§2.5.4）
- `MealLog.eatenAtSource`：`now` | `exif` | `mtime` | `manual`（補記時可回頭查是誰決定了時間）
- 補記佇列暫存：`modules/desktopst.nutrition/pending/`（照片副本＋估算結果＋狀態，完成或跳過即清）
- 照片存 `modules/desktopst.nutrition/photos/`，**不進 APK、不進搬家包以外的地方**

純函式進 `core/`（可測、可注入 `now`）：

| 函式 | 職責 |
|---|---|
| `matchFoodItem(name, brand, library)` | 正規化比對，回傳 0/1/N 候選 |
| `buildPhotoEstimatePrompt(recentNames)` | 組 prompt（不含個資） |
| `parseEstimateResult(raw)` | 寬鬆解析 JSON，缺欄位標記而非丟錯 |
| `applyEstimateToEntries(result, choice)` | 產出要寫入的 `FoodItem?` ＋ `MealLog` |
| `resolveEatenAt(exif, mtime, now)` | 依 §2.5.3 優先序決定時間與 `eatenAtSource`（可注入 `now`） |
| `hashPhoto(bytes)` / `findDuplicateLog(hash, logs)` | 補記去重（§2.5.4） |
| `resolveMaxFoodSlots(caps, currentPhotoCount)` | 依模型能力算目前還能加幾份食物（§2.9.2） |
| `estimateRequestCost(caps, photos, promptLen)` | 送出前費用預估，未知則回 `null`（§2.9.3） |
| `checkRequestCompatibility(caps, request)` | 送出前相容性檢查（§2.9.4） |
| `parsePastedNutrition(text)` | 從貼上的文字抓出 kcal／蛋白（§2.10.3，**不呼叫模型**） |
| `normalizeLabel(label, eatenPortion)` | 每100g／每份／每包 → 實際吃下去的 kcal／蛋白／碳水／脂肪／糖／鈉（§2.6.2，**算術本機做**，缺值回 `null`） |
| `nutritionFromGrams(label, grams)` | 秤重模式換算（§2.8.2），三種標示基準都要過測試 |
| `stepServings(current, dir)` / `formatServings(v)` | 份量欄級距 1/3→1/2→1→2→…→10 與分數顯示（§2.7.3） |

`src/mobile/` 與 `mobileServer` 只做薄轉呼叫（CLAUDE.md §5）。

## 8. 驗收標準

1. 新食物從開 App 到記錄完成 **≤ 4 次觸控**（含送出前補充頁按一次「估算」）、**不需打字**。
2. 已吃過的食物再記一次 **不呼叫 LLM**（可由 log 驗證 token 用量為 0）。
3. AI 失敗／逾時時，使用者仍能在 3 步內用手動輸入完成記錄。
4. 同一食物第二次記錄，熱量數字與第一次**完全一致**（解決「隔天熱量漂」痛點）。
5. 任何自動行為都不會在未經明示下改寫既有 `FoodItem` 的營養值。
6. **補記：** 從相簿選 3 張中午拍的照片，全部記錄完成 **≤ 6 次觸控、不需打字、不需手選日期**，且三筆都落在拍照的那一天／那個時間。
7. **補記去重：** 同一張照片再選一次，預設不會產生第二筆紀錄。
8. 補記途中關閉 App 再開啟，未處理的照片與已算好的結果仍在。
9. **多份：** 手動放 3 份食物（各 1～3 張）→ 一次請求 → 翻頁確認 → 一顆「全部存入」寫入 3 筆；中途失敗不留半套。
10. **上限隨模型：** 切換到 `maxImagesPerRequest` 較小的模型後，可加份數立刻縮減並顯示提示，不是寫死的數字。
11. **費用：** 估算前顯示目前模型與預估費用；本地模型顯示「無 API 費用」；未知模型顯示「費用未知」且不擋操作。
11b. **幣別：** 金額一律帶 ISO 幣別代碼且不做換算；單價缺 `currency` 視同缺價；小額不顯示為 `$0.00`。
11d. **重估：** 對一筆只有熱量／蛋白的舊食物按「重新估算」→「只補空白欄」，結果只填入原本是空的碳水/脂肪/糖/鈉，熱量/蛋白數字不變。
11e. **重估不擋歷史：** 重估並套用新值後，過去已記錄的 `MealLog` 熱量顯示不追溯改變說明以外的行為（沿用既有「改主檔全部跟著變」設計，僅要求 UI 有提示文字）。
11c. **碳水／脂肪／糖／鈉：** 拍照或秤重估算時一併回存 `carbsG`／`fatG`／`sugarG`／`sodiumMg`；結果卡主要視圖**不顯示**這四欄（收在「更多」／詳情），估不到時存 `null` 而非 0 或瞎猜值；日後報表或提醒功能要用時資料已經在，不需回頭重估。
12. **四步完成：** 新食物從開 App 到記錄完成 ≤ 4 次觸控，且補充說明留白時全程不需打字。
13. **標示優先：** 拍「封面＋營養成分表＋內容物」三張，結果的 kcal／蛋白**等於標示換算值**（不是模型經驗值），來源徽章顯示「依營養標示」，且三張合起來只呼叫一次 LLM。
14. **換算正確：** 標示為「每 100 公克 250 kcal，每份 60 公克，本包裝含 2 份」而你吃整包 → 存入 300 kcal。三種基準各有單元測試。
15. **只拍成分表：** 單張成分表可完成記錄；命中庫內同品項時沿用庫內數字，且不會自動覆寫食物庫。
16. **文字優先：** 補充說明寫「吃了半份」而圖片看起來是整份 → 結果依半份計，且結果卡顯示 `noteConflict` 那行小字。
17. **份量欄：** `−`／`＋` 走 1/3→1/2→1→2→…→10 且到底不溢出；點數字可手打 0.75 這種級距外的值。
18. **秤重：** 拍一張「每100公克」標示、輸入 12 g → 熱量等於標示 ÷100×12；「每一份量 X 公克」的標示也算得出同樣結果。
19. **記憶：** 同一零食第二次記錄，份量欄預設帶出上次的 `12 g`。
20. **開關關閉時：** 所有拍照／補記入口消失（非變灰）、無任何引導提示、不發出任何 LLM 請求；
    關鍵字入帳、手建食物、秤重換算、份量欄、既有 AI 紀錄的顯示**全部照常可用**。
21. **可逆：** 關閉再開啟，模型設定與既有資料原封不動。
22. **貼上解析：** 貼入「熱量 320 大卡，蛋白質 18 克」可自動填入兩欄，且過程零網路請求。
23. **絕不掃相簿：** 全程不請求相簿讀取權限、不存取使用者未當次選取的任何照片。

## 9. 待 owner 拍板

- 結果卡是否顯示 AI 的 `note`（增加信任 vs 增加閱讀量）→ 建議**顯示一行小字**。
- `confidence: low` 是否仍允許一鍵存 → 建議**允許**（理由見 §3.2）。
- 一張照片含多樣食物（便當）→ 第一期建議**當成一筆**估總熱量；拆項留 P5。
- （§2.9 的兩題已於 2026-08-19 拍板：未知模型上限 3 份；費用只顯示原幣別、清楚標示幣別。）
- 鈉／糖之後要不要比照熱量／蛋白，升級成「有日上限、超標提醒」的一等欄位？
  這期先當純備查存起來，等資料累積一陣子、owner 有感覺再決定要不要做警示（見 §1 原則 7b）。
- 補記結果卡是否預設提供「全部存入」（§2.5.2 變體）→ 建議**先不做**，P3 之後看實際錯誤率再決定。
- 首屏「有 3 張照片還沒記錄」的相簿掃描提示要不要做 → 需相簿讀取權限，建議**預設關**、設定內可開。
- 是否記錄 AI 原始回應以便日後校準 → 建議存最近 50 筆於本機 debug log，可關。
