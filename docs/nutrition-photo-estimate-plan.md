# 拍照估熱量（Photo → AI 估算）—— 實作規劃

> 狀態：**規劃中，尚未實作。** 屬於飲食模組（`desktopst.nutrition`）B9b 的先行切片。
> 最後更新：2026-08-19（補「相簿補記」§2.5、「一餐多張與營養成分表」§2.6；移除相簿掃描提示）。
> 母規格：`docs/future-nutrition-module.md`（資料模型／搬家包／範圍以母規格為準，本文件不重述）。
> 與「小工具（Widget）」二選一時：**先做本項**（owner 每天的真痛點是入帳，不是看數字）。

---

## 0. 一句話

拍一張照 → AI 估出「名稱＋熱量＋蛋白」→ 一鍵存入 → 同時寫進**食物庫**與**今日餐次**；
估錯才進「修改模式」對話式調整再回存，正常路徑**不打字、不看表單**。
> 兩條入口：**即時拍**（§2）與**回家用相簿補記**（§2.5），共用同一套結果卡與回存邏輯。

---

## 1. 設計原則（本文件的硬規則）

1. **三步以內完成新食物入帳**：拍照 → 看一眼結果 → 存。中間**不得**插入必填表單、分類選擇、份量輪盤。
2. **預設值必須夠好，讓使用者可以不看**：份量預設 1 份、時間預設現在、餐別由時間推算。全部可事後改。
3. **修改是例外路徑**：只有按下「不對」才展開。修改成本可以高一點，但不得污染正常路徑。
4. **AI 只在新食物出現**：拍照後先過本機比對；命中舊食物直接沿用營養（母規格 §3.2 的「庫內禁止 LLM 覆寫」照舊）。
5. **有標示就不准猜**：照片裡若有營養成分表，數字一律以標示為準，LLM 只負責讀出來（OCR＋換算），不得用「一般三明治大約…」覆蓋（§2.6）。
6. **絕不主動掃相簿**：只讀使用者當次明確選取的照片。不要求相簿讀取權限、不做背景掃描、不做「你有幾張沒記錄」提示 —— 相簿裡不是只有食物。
7. **一次呼叫、一次結果**：不做多輪自動追問；AI 一次回不完整就顯示缺欄位讓使用者點。

## 2. 正常路徑（Happy Path）

### 2.1 三步

```
[1] 飲食入口／快覽 → 按「拍照記錄」（相機直接開，不先進中介頁）
        ↓ 拍完或從相簿選（accept 只給 image/*）
[2] 結果卡（3～6 秒內出現）
        燻雞三明治 · 7-11
        約 320 kcal · 蛋白 18 g · 1 份
        [ 存入 ]   [ 不對，我改 ]
        ↓ 按「存入」
[3] 完成：Toast「已記錄 · 今日 1180 / 1800 kcal」，回到快覽／今日列表
```

實際觸控次數：開相機 1、快門 1、存入 1 —— **3 touch**。
從相簿選則是 開相簿 1、選圖 1、存入 1，同樣 3 touch。

### 2.2 「存入」到底做了什麼（單一動作、兩筆寫入）

| 情況 | 行為 |
|---|---|
| 比對到既有 `FoodItem`（信心足） | **不新建**：只寫一筆 `MealLog`（foodItemId 沿用、servings 用估的、eatenAt=now）；照片可選附在 MealLog |
| 未命中 → 新食物 | 新建 `FoodItem`（name／brand／flavor／perServing／photoKeys[0]＝這張照片、source=`llm-photo`）＋ 寫一筆 `MealLog` |

兩者都由一顆按鈕完成，UI 不讓使用者選「要不要建食物庫」——**新食物一律進庫**，否則下次還要再估一次（違反母規格「熟食重複記帳趨近零 token」）。

### 2.3 相片命中既有食物的判定（免 LLM 或省 LLM）

順序：

1. **最近清單快捷**：結果卡上方常駐一列「最近吃過」（依 `lastEatenAt`／`useCount`），使用者其實常常在拍照前就能一點命中 → 那條路徑是 **2 touch**，不走 AI。
2. **AI 回傳名稱後比對本機庫**：以 `name` + `aliases` + `brand` 做正規化比對（`core/` 純函式）。
   - 命中唯一 → 結果卡直接顯示庫內營養，並標示「沿用你的紀錄（已記錄 12 次）」；**不採用 AI 的數字**。
   - 命中多筆 → 結果卡下方列出候選（副標＝品牌／口味＋每份 kcal＋上次食用，規則同母規格 §3.2b），點一下即代入，仍是 3 touch。
   - 未命中 → 用 AI 估的數字，新建。

> 不做影像特徵比對／向量檢索。第一期只靠「AI 出名稱 → 文字比對」，成本低且可測。

## 2.5 補記路徑（相簿補登）—— 在外只來得及拍照，回家再記

這是 owner 的**第二種主要情境**，不是邊角案例：外面時間只夠開系統相機按快門，
沒空開 App、沒空打字；回家（或當晚、隔天）才用相簿裡那幾張照片補記錄。

### 2.5.1 設計要點

1. **在外不需要動到 DeST**：用手機原生相機即可。App 不強迫使用者從我們的入口拍照。
2. **時間必須回填成當時**，不是補記當下 —— 否則整份熱量記錄的日期會全錯（見 §2.5.3）。
3. **一次處理多張**：一天可能有 3～4 餐都是這樣拍的，必須批次，不能一張一張重來三步。
4. **不要求使用者記得哪張是哪餐**：靠 EXIF 時間自動歸日、歸餐別。

### 2.5.2 三步（批次補記）

```
[1] 飲食入口 → 「從相簿補記」
        ↓ 系統相簿多選（accept 只給 image/*，不列副檔名）
        ↓ 選 3 張 → 確定
[2] 佇列逐張出結果卡（背景已同時送出估算，滑到下一張時通常已算好）
        午餐 · 8/19 12:34（取自照片時間）
        燻雞三明治 · 7-11 · 約 320 kcal · 蛋白 18 g
        [ 存入 ]  [ 不對，我改 ]  [ 跳過這張 ]
        ↓ 每張按一次「存入」
[3] 完成頁：「已補記 3 筆 · 8/19 共 1480 kcal」
```

觸控數：開相簿 1、多選 N、確定 1、每張存入 1 → **N 張 = N + 3 次**，
且**完全不需打字**、不需自己挑日期時間。單張時退化為 3 touch，與正常路徑一致。

> 更快的變體（P3 再評估）：結果卡提供「全部存入」一顆按鈕，
> 只在 `confidence: low` 或比對到多筆候選的那幾張停下來讓人確認 →
> 3 張也可能只要 4 touch。預設**不**開啟全部存入，避免整批錯記難收拾。

### 2.5.3 時間怎麼決定（重要）

優先序，取第一個有值的：

| 來源 | 說明 |
|---|---|
| **EXIF `DateTimeOriginal`** | 主要來源。相簿照片幾乎都有 |
| 檔案 mtime／`File.lastModified` | EXIF 被相簿 App 洗掉時的退路 |
| 使用者手選 | 前兩者都沒有 → 結果卡上的時間顯示為可點的「請確認時間」，**此時才要求互動** |

- 結果卡上永遠**顯示**那個時間（`8/19 12:34`），讓使用者一眼看出是不是補記到對的那天。
- 餐別（早／午／晚／點心）由時間推算，只是顯示用標籤，不影響資料。
- **時區**：以拍照當下的本機時區解讀 EXIF（EXIF 常無時區資訊，第一期就用裝置目前時區，出國補記可能差幾小時 → 由使用者在卡上手改）。
- 跨日補記合法：`MealLog.eatenAt` 寫回當時，今日列表／合計自然歸到正確那一天。

### 2.5.4 已補記過的照片不要重複入帳

批次補記最容易踩的坑是「上次選過的照片這次又選到」。

- 每張照片存檔時記錄一個**內容指紋**（檔案 bytes 的 hash，`core/` 純函式），存在 `MealLog.photoHash`。
- 選圖後先比對指紋：命中 → 該張直接標記「已記錄過（8/19 12:34 燻雞三明治）」，
  **預設跳過**，但保留「仍要再記一筆」按鈕（真的吃了兩份的情況）。
- 指紋只在本機比對，不上傳。

### 2.5.5 佇列與失敗

- 選 N 張後**併發上限 2～3 張**送估算（避免一次打爆 API 與流量），其餘排隊；使用者看第 1 張時第 2、3 張通常已備妥。
- 單張失敗（逾時／解析失敗）→ 該張留在佇列標紅，不擋後面；最後在完成頁列出「2 筆待處理」，可重試或手動輸入。
- 中途離開 App → **佇列要持久化**（存模組資料目錄的暫存區，含已複製的照片與已得到的估算結果），回來可續。這是相簿補記與即時拍照最大的實作差異。
- 使用者按「跳過這張」→ 該照片不入帳、暫存清掉，指紋也不記錄（下次還可以再選）。

### 2.5.6 桌面版

同一條路徑：把幾張照片一次拖進飲食面板 → 走同一個佇列與結果卡。
桌面讀 EXIF 更容易，且「在外拍、回家用電腦補」也是 owner 會用的組合。

## 2.6 一餐多張照片與營養成分表（實際拍法）

owner 的真實拍法不是「一餐一張美照」，第一期就要吃得下這三種：

| 拍法 | 照片組成 | 誰決定營養數字 |
|---|---|---|
| A. 包裝食品完整拍 | 封面／包裝正面 ＋ **營養成分表** ＋ 實際內容物（2～3 張） | **成分表**（正面只用來取名稱／品牌） |
| B. 常吃的包裝食品 | **只有營養成分表**一張 | 成分表；名稱靠比對既有食物庫或標示上的品名 |
| C. 紙袋／包裝紙裹著的即食品 | 一張，食物被紙袋遮住一部分（如三明治、蛋餅、餅類） | 無標示 → LLM 估，但要處理遮蔽（§2.6.4） |

### 2.6.1 多張＝一餐怎麼組（不增加操作步驟）

選了 5 張照片，其中 3 張是同一個便當，不能逼使用者手動框選。

- **自動分組**：拍攝時間（EXIF）相隔 **≤ 2 分鐘**的照片，預設視為**同一餐的多張**，合成一張「組卡」。
  - 依據：包裝食品的封面／成分表／內容物幾乎都是連拍的；不同餐至少隔幾十分鐘。
- 組卡上橫排縮圖，每張下面標角色（`正面` / `成分表` / `內容物`，由 LLM 判定）。
- **拆開**：組卡右上「這不是同一餐」→ 拆成各自獨立的卡（1 touch，例外路徑）。
- **合併**：相鄰兩張卡若被誤拆，卡片間有「合併」細鈕。
- 分組純函式進 `core/`：`groupPhotosByTime(photos, gapMinutes)`，門檻可在設定改（預設 2 分鐘）。

> 一組多張**只呼叫一次 LLM**（多圖單次請求），不是每張各叫一次 —— 省 token，也避免三張各給一組矛盾的數字。

### 2.6.2 營養成分表是最高優先來源

LLM 輸出改為帶來源標記：

```jsonc
{
  "name": "燻雞三明治",
  "brand": "7-11",
  "nutritionSource": "label",   // label | estimate | label-partial
  "label": {                     // 只有讀到成分表時才有
    "basis": "per100g",         // per100g | perServing | perPackage
    "servingSizeG": 60,
    "servingsPerPackage": 2,
    "kcal": 250,
    "proteinG": 9
  },
  "perServing": { "kcal": 300, "proteinG": 10.8 },  // 換算後、實際吃下去的一份
  "eatenPortion": 1,             // 這次吃了整包／半包
  "confidence": "high"
}
```

規則：

1. 組內**任一張**讀到成分表 → `nutritionSource: "label"`，`perServing` 必須由 `label` 換算得出，**不得**是模型的經驗值。
2. 換算是**本機純函式**做的，不是叫 LLM 算數：
   `normalizeLabel(label, eatenPortion)` → `{ kcal, proteinG }`（`core/`，可測）。
   台灣標示常見三種基準都要支援：`每100公克` / `每一份量 X 公克，本包裝含 Y 份` / `每包裝`。
   **模型只負責把表上的字讀成結構化欄位，算術一律本機做** —— 模型算錯的機率遠高於讀錯。
3. 表格數字缺一半（拍糊、被反光蓋掉）→ `label-partial`：讀到的用標示、缺的標成「？」，結果卡把該欄變成待補的可點欄位，仍可直接存（存成 0 或空，不阻擋）。
4. **結果卡要顯示來源徽章**：`依營養標示` / `AI 估算` / `標示不完整`。你一眼就知道這筆數字可不可信 —— 這比多一位小數重要。
5. 存進食物庫時 `FoodItem.source` 記為 `label` 的那些，**日後不再被任何 LLM 路徑覆寫**（比 `llm-photo` 更硬）。

### 2.6.3 只拍成分表（拍法 B）

- 組內沒有正面照 → 名稱來源依序：成分表照片上的**品名文字** → 比對既有食物庫（同品牌＋相近數字）→ 都沒有就用 `未命名（依標示）` 並**在結果卡把名稱欄變成第一個可點的欄位**。
- 命中既有食物時，結果卡顯示「符合你庫裡的『燻雞三明治 · 7-11』（已記錄 12 次）」，一鍵存＝只寫 `MealLog`，數字沿用庫內。
- 若庫內數字與這次讀到的標示**不一致**（廠商改配方／你記錯）→ 卡上顯示兩組數字並提供「更新食物庫為新標示」按鈕，**預設不更新**（守住母規格「庫內禁止 LLM 覆寫」）。

### 2.6.4 紙袋／包裝紙遮住（拍法 C）

沒有標示可讀，只能估，但要估得比「看到麵包就 250 kcal」好：

- prompt 明確告知**食物可能被包裝紙、紙袋、餐盒部分遮住**，要求模型：
  - 只根據**可見部分**推論內容物，看不到的餡料**不要編**（寧可 `confidence: medium`）；
  - 用可見的麵包片數／厚度／相對紙袋的尺寸推**份量**，而不是預設一份；
  - 包裝紙上的**店家標誌／印刷字樣**要拿來當品牌線索（如你這張的包裝紙圖樣）。
- 這類食物多半是**你的常吃品項** → 最有效的其實不是模型變聰明，而是 §2.3 的比對：第一次記完進庫、之後同一家的三明治直接命中沿用，數字永遠一致。
- 結果卡對這類會顯示 `AI 估算` 徽章 ＋ 一行「看到：白吐司、生菜、醬料；紙袋遮住內餡」，讓你能判斷要不要按「不對，我改」。

### 2.6.5 對 §2.2「存入」的影響

一組多張存入時：
- `FoodItem.photoKeys` 依序放 **正面 → 成分表 → 內容物**（母規格上限 3 張，剛好對應）；
- 成分表那張特別重要（日後查證用），若超過 3 張要取捨，**成分表優先保留**；
- `MealLog` 仍只有一筆，`photoHash` 取組內第一張，其餘張的 hash 一併記錄以免重複入帳。

## 3. AI 呼叫規格

### 3.1 輸入

- **一組**壓縮後照片（1～3 張，同一次請求；分組規則見 §2.6.1）。長邊上限約 1024px、JPEG q≈0.7。
  **例外**：被判定為營養成分表的那張用較高解析度（長邊 1568px 以上）送出，小字才讀得準；壓太狠會讀錯數字。
- 可選短註（使用者若有打字才帶；正常路徑沒有）
- 指示模型：**若任一張是營養成分表，必須逐欄讀出並填 `label`，不得改用經驗值**；食物可能被包裝紙遮蔽（§2.6.4）
- 本機提示：使用者最近／最常吃的 **食物名稱清單（僅名稱，20～40 筆）**，讓模型優先吐出既有名稱以提高命中率。**不送**營養數字、不送體重／上限等個資。

### 3.2 輸出（強制 JSON）

> 完整欄位（含 `label` / `nutritionSource`）見 §2.6.2；以下為無標示時的最小形狀。

```jsonc
{
  "name": "燻雞三明治",
  "brand": "7-11",          // 不確定則 null
  "flavor": null,
  "servings": 1,            // 照片中看到的份數
  "perServing": { "kcal": 320, "proteinG": 18 },
  "confidence": "high",     // high | medium | low
  "note": "三明治，內含雞肉與生菜"   // 一句話，給使用者判斷是否辨識錯
}
```

- 解析失敗／缺欄位 → 不報錯畫面，改顯示「只認出：___，請補熱量」的最小補填卡（仍可一鍵存）。
- `confidence: low` → 結果卡把數字改成**可點的**灰字並提示「不太確定，點數字可改」，但**仍允許直接存**（使用者的容忍度比正確率重要，之後隨時可改）。

### 3.3 模型與設定

- 走母規格 §3.4：`nutrition.llm` 獨立設定，預設挑便宜的 vision 模型，與角色主模型分開。
- 逾時 12 秒；失敗給「重試 / 手動輸入 / 取消」三顆。重試不重新壓縮照片。

## 4. 例外路徑：「不對，我改」

按下後才展開，分兩種修法，同一張卡上切換：

### 4.1 快改（多數情況）

結果卡就地變成可編輯：名稱、品牌、kcal、蛋白、份量、時間。
改完按「存入」，寫入時 `source` 標記為 `llm-photo-edited`（之後可統計 AI 準確度）。

### 4.2 對話式修（辨識完全錯／要重估）

一個輸入框：「這是滷雞腿便當，不是雞排飯」→ 帶著**原照片＋原結果＋這句話**再呼叫一次，回新的結果卡。
- 最多允許連續 3 次（避免無限燒 token），超過提示改用快改。
- 每次都是完整重估，不做增量 patch（實作簡單、結果可預期）。

### 4.3 回存規則

| 情境 | 行為 |
|---|---|
| 新食物、改過 | 建立 `FoodItem` 用**改後**的值 |
| 命中舊食物、只是這次份量不同 | **只改 `MealLog.servings`**，不動 `FoodItem` |
| 命中舊食物、但發現主檔數字本來就錯 | 需在卡上明確按「同時更新食物庫」才覆寫 `FoodItem`（預設不勾）——守住母規格「庫內禁止 LLM 覆寫」 |
| 其實是不同食物被比對錯 | 提供「另存為新食物」（母規格 §3.2b 已有此操作，共用同一段邏輯） |

## 6. 資料與檔案落點

沿用母規格 §4，不新增實體。本模組新增／使用的欄位：

- `FoodItem.source`：`manual` | `label` | `llm-photo` | `llm-photo-edited`（`label` 最硬，不被任何 LLM 路徑覆寫）
- `FoodItem.labelRaw?`：讀到的原始標示欄位（basis／每份克數／每包份數），供日後查證與重算
- `FoodItem.photoKeys[0]`：拍照建立時自動填入這張照片
- `MealLog.photoKey?`：當次照片（與食物庫照片不同張時才存，避免重複佔空間）
- `MealLog.photoHash?` / `photoHashes[]`：照片內容指紋（一組多張時全記），用於補記時避免重複入帳（§2.5.4）
- `MealLog.eatenAtSource`：`now` | `exif` | `mtime` | `manual`（補記時可回頭查是誰決定了時間）
- 補記佇列暫存：`modules/desktopst.nutrition/pending/`（照片副本＋估算結果＋狀態，完成或跳過即清）
- 照片存 `modules/desktopst.nutrition/photos/`，**不進 APK、不進搬家包以外的地方**

純函式進 `core/`（可測、可注入 `now`）：

| 函式 | 職責 |
|---|---|
| `matchFoodItem(name, brand, library)` | 正規化比對，回傳 0/1/N 候選 |
| `buildPhotoEstimatePrompt(recentNames)` | 組 prompt（不含個資） |
| `parseEstimateResult(raw)` | 寬鬆解析 JSON，缺欄位標記而非丟錯 |
| `applyEstimateToEntries(result, choice)` | 產出要寫入的 `FoodItem?` ＋ `MealLog` |
| `resolveEatenAt(exif, mtime, now)` | 依 §2.5.3 優先序決定時間與 `eatenAtSource`（可注入 `now`） |
| `hashPhoto(bytes)` / `findDuplicateLog(hash, logs)` | 補記去重（§2.5.4） |
| `groupPhotosByTime(photos, gapMinutes)` | 多張照片自動分組成「一餐」（§2.6.1） |
| `normalizeLabel(label, eatenPortion)` | 每100g／每份／每包 → 實際吃下去的 kcal 與蛋白（§2.6.2，**算術本機做**） |

## 8. 驗收標準

1. 新食物從開 App 到記錄完成 **≤ 3 次觸控**、**不需打字**。
2. 已吃過的食物再記一次 **不呼叫 LLM**（可由 log 驗證 token 用量為 0）。
3. AI 失敗／逾時時，使用者仍能在 3 步內用手動輸入完成記錄。
4. 同一食物第二次記錄，熱量數字與第一次**完全一致**（解決「隔天熱量漂」痛點）。
5. 任何自動行為都不會在未經明示下改寫既有 `FoodItem` 的營養值。
6. **補記：** 從相簿選 3 張中午拍的照片，全部記錄完成 **≤ 6 次觸控、不需打字、不需手選日期**，且三筆都落在拍照的那一天／那個時間。
7. **補記去重：** 同一張照片再選一次，預設不會產生第二筆紀錄。
8. 補記途中關閉 App 再開啟，未處理的照片與已算好的結果仍在。
9. **標示優先：** 拍「封面＋營養成分表＋內容物」三張，結果的 kcal／蛋白**等於標示換算值**（不是模型經驗值），來源徽章顯示「依營養標示」，且三張合起來只呼叫一次 LLM。
10. **換算正確：** 標示為「每 100 公克 250 kcal，每份 60 公克，本包裝含 2 份」而你吃整包 → 存入 300 kcal。三種基準各有單元測試。
11. **只拍成分表：** 單張成分表可完成記錄；命中庫內同品項時沿用庫內數字，且不會自動覆寫食物庫。
12. **絕不掃相簿：** 全程不請求相簿讀取權限、不存取使用者未當次選取的任何照片。

## 9. 待 owner 拍板

- 結果卡是否顯示 AI 的 `note`（增加信任 vs 增加閱讀量）→ 建議**顯示一行小字**。
- `confidence: low` 是否仍允許一鍵存 → 建議**允許**（理由見 §3.2）。
- 一張照片含多樣食物（便當）→ 第一期建議**當成一筆**估總熱量；拆項留 P5。
- 自動分組的時間門檻（預設 2 分鐘）是否合用 → 你實際拍封面到拍成分表大概間隔多久，決定後改預設值。
- 吃「半包」這種情況要不要在結果卡上放快捷（½ / 1 / 2）→ 建議**放**，包裝食品很常吃不完整包，且比打數字快。
- 補記結果卡是否預設提供「全部存入」（§2.5.2 變體）→ 建議**先不做**，P3 之後看實際錯誤率再決定。
- 首屏「有 3 張照片還沒記錄」的相簿掃描提示要不要做 → 需相簿讀取權限，建議**預設關**、設定內可開。
- 是否記錄 AI 原始回應以便日後校準 → 建議存最近 50 筆於本機 debug log，可關。
