# 拍照估熱量（Photo → AI 估算）—— 實作規劃

> 狀態：**規劃中，尚未實作。** 屬於飲食模組（`desktopst.nutrition`）B9b 的先行切片。
> 最後更新：2026-08-19。
> 母規格：`docs/future-nutrition-module.md`（資料模型／搬家包／範圍以母規格為準，本文件不重述）。
> 與「小工具（Widget）」二選一時：**先做本項**（owner 每天的真痛點是入帳，不是看數字）。

---

## 0. 一句話

拍一張照 → AI 估出「名稱＋熱量＋蛋白」→ 一鍵存入 → 同時寫進**食物庫**與**今日餐次**；
估錯才進「修改模式」對話式調整再回存，正常路徑**不打字、不看表單**。

---

## 1. 設計原則（本文件的硬規則）

1. **三步以內完成新食物入帳**：拍照 → 看一眼結果 → 存。中間**不得**插入必填表單、分類選擇、份量輪盤。
2. **預設值必須夠好，讓使用者可以不看**：份量預設 1 份、時間預設現在、餐別由時間推算。全部可事後改。
3. **修改是例外路徑**：只有按下「不對」才展開。修改成本可以高一點，但不得污染正常路徑。
4. **AI 只在新食物出現**：拍照後先過本機比對；命中舊食物直接沿用營養（母規格 §3.2 的「庫內禁止 LLM 覆寫」照舊）。
5. **一次呼叫、一次結果**：不做多輪自動追問；AI 一次回不完整就顯示缺欄位讓使用者點。

## 2. 正常路徑（Happy Path）

### 2.1 三步

```
[1] 飲食入口／快覽 → 按「拍照記錄」（相機直接開，不先進中介頁）
        ↓ 拍完或從相簿選（accept 只給 image/*）
[2] 結果卡（3～6 秒內出現）
        燻雞三明治 · 7-11
        約 320 kcal · 蛋白 18 g · 1 份
        [ 存入 ]   [ 不對，我改 ]
        ↓ 按「存入」
[3] 完成：Toast「已記錄 · 今日 1180 / 1800 kcal」，回到快覽／今日列表
```

實際觸控次數：開相機 1、快門 1、存入 1 —— **3 touch**。
從相簿選則是 開相簿 1、選圖 1、存入 1，同樣 3 touch。

### 2.2 「存入」到底做了什麼（單一動作、兩筆寫入）

| 情況 | 行為 |
|---|---|
| 比對到既有 `FoodItem`（信心足） | **不新建**：只寫一筆 `MealLog`（foodItemId 沿用、servings 用估的、eatenAt=now）；照片可選附在 MealLog |
| 未命中 → 新食物 | 新建 `FoodItem`（name／brand／flavor／perServing／photoKeys[0]＝這張照片、source=`llm-photo`）＋ 寫一筆 `MealLog` |

兩者都由一顆按鈕完成，UI 不讓使用者選「要不要建食物庫」——**新食物一律進庫**，否則下次還要再估一次（違反母規格「熟食重複記帳趨近零 token」）。

### 2.3 相片命中既有食物的判定（免 LLM 或省 LLM）

順序：

1. **最近清單快捷**：結果卡上方常駐一列「最近吃過」（依 `lastEatenAt`／`useCount`），使用者其實常常在拍照前就能一點命中 → 那條路徑是 **2 touch**，不走 AI。
2. **AI 回傳名稱後比對本機庫**：以 `name` + `aliases` + `brand` 做正規化比對（`core/` 純函式）。
   - 命中唯一 → 結果卡直接顯示庫內營養，並標示「沿用你的紀錄（已記錄 12 次）」；**不採用 AI 的數字**。
   - 命中多筆 → 結果卡下方列出候選（副標＝品牌／口味＋每份 kcal＋上次食用，規則同母規格 §3.2b），點一下即代入，仍是 3 touch。
   - 未命中 → 用 AI 估的數字，新建。

> 不做影像特徵比對／向量檢索。第一期只靠「AI 出名稱 → 文字比對」，成本低且可測。

## 3. AI 呼叫規格

### 3.1 輸入

- 一張壓縮後照片（長邊上限約 1024px、JPEG q≈0.7；壓縮在存檔前做，庫內照片也用同一份）
- 可選短註（使用者若有打字才帶；正常路徑沒有）
- 本機提示：使用者最近／最常吃的 **食物名稱清單（僅名稱，20～40 筆）**，讓模型優先吐出既有名稱以提高命中率。**不送**營養數字、不送體重／上限等個資。

### 3.2 輸出（強制 JSON）

```jsonc
{
  "name": "燻雞三明治",
  "brand": "7-11",          // 不確定則 null
  "flavor": null,
  "servings": 1,            // 照片中看到的份數
  "perServing": { "kcal": 320, "proteinG": 18 },
  "confidence": "high",     // high | medium | low
  "note": "三明治，內含雞肉與生菜"   // 一句話，給使用者判斷是否辨識錯
}
```

- 解析失敗／缺欄位 → 不報錯畫面，改顯示「只認出：___，請補熱量」的最小補填卡（仍可一鍵存）。
- `confidence: low` → 結果卡把數字改成**可點的**灰字並提示「不太確定，點數字可改」，但**仍允許直接存**（使用者的容忍度比正確率重要，之後隨時可改）。

### 3.3 模型與設定

- 走母規格 §3.4：`nutrition.llm` 獨立設定，預設挑便宜的 vision 模型，與角色主模型分開。
- 逾時 12 秒；失敗給「重試 / 手動輸入 / 取消」三顆。重試不重新壓縮照片。

## 4. 例外路徑：「不對，我改」

按下後才展開，分兩種修法，同一張卡上切換：

### 4.1 快改（多數情況）

結果卡就地變成可編輯：名稱、品牌、kcal、蛋白、份量、時間。
改完按「存入」，寫入時 `source` 標記為 `llm-photo-edited`（之後可統計 AI 準確度）。

### 4.2 對話式修（辨識完全錯／要重估）

一個輸入框：「這是滷雞腿便當，不是雞排飯」→ 帶著**原照片＋原結果＋這句話**再呼叫一次，回新的結果卡。
- 最多允許連續 3 次（避免無限燒 token），超過提示改用快改。
- 每次都是完整重估，不做增量 patch（實作簡單、結果可預期）。

### 4.3 回存規則

| 情境 | 行為 |
|---|---|
| 新食物、改過 | 建立 `FoodItem` 用**改後**的值 |
| 命中舊食物、只是這次份量不同 | **只改 `MealLog.servings`**，不動 `FoodItem` |
| 命中舊食物、但發現主檔數字本來就錯 | 需在卡上明確按「同時更新食物庫」才覆寫 `FoodItem`（預設不勾）——守住母規格「庫內禁止 LLM 覆寫」 |
| 其實是不同食物被比對錯 | 提供「另存為新食物」（母規格 §3.2b 已有此操作，共用同一段邏輯） |

## 6. 資料與檔案落點

沿用母規格 §4，不新增實體。本模組新增／使用的欄位：

- `FoodItem.source`：`manual` | `llm-photo` | `llm-photo-edited`
- `FoodItem.photoKeys[0]`：拍照建立時自動填入這張照片
- `MealLog.photoKey?`：當次照片（與食物庫照片不同張時才存，避免重複佔空間）
- 照片存 `modules/desktopst.nutrition/photos/`，**不進 APK、不進搬家包以外的地方**

純函式進 `core/`（可測、可注入 `now`）：

| 函式 | 職責 |
|---|---|
| `matchFoodItem(name, brand, library)` | 正規化比對，回傳 0/1/N 候選 |
| `buildPhotoEstimatePrompt(recentNames)` | 組 prompt（不含個資） |
| `parseEstimateResult(raw)` | 寬鬆解析 JSON，缺欄位標記而非丟錯 |
| `applyEstimateToEntries(result, choice)` | 產出要寫入的 `FoodItem?` ＋ `MealLog` |

`src/mobile/` 與 `mobileServer` 只做薄轉呼叫（CLAUDE.md §5）。

## 8. 驗收標準

1. 新食物從開 App 到記錄完成 **≤ 3 次觸控**、**不需打字**。
2. 已吃過的食物再記一次 **不呼叫 LLM**（可由 log 驗證 token 用量為 0）。
3. AI 失敗／逾時時，使用者仍能在 3 步內用手動輸入完成記錄。
4. 同一食物第二次記錄，熱量數字與第一次**完全一致**（解決「隔天熱量漂」痛點）。
5. 任何自動行為都不會在未經明示下改寫既有 `FoodItem` 的營養值。

---

## 9. 待 owner 拍板

- 結果卡是否顯示 AI 的 `note`（增加信任 vs 增加閱讀量）→ 建議**顯示一行小字**。
- `confidence: low` 是否仍允許一鍵存 → 建議**允許**（理由見 §3.2）。
- 一張照片含多樣食物（便當）→ 第一期建議**當成一筆**估總熱量；拆項留 P5。
- 是否記錄 AI 原始回應以便日後校準 → 建議存最近 50 筆於本機 debug log，可關。
