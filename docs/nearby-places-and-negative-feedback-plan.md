# 附近地點推薦＋負向關鍵字快速回饋 — 構想文件

> 狀態：**構想階段，未定案、未開工**。本文件整理與 owner 的討論結論，供之後排進 `TODO.md` 前的參考。
> 緣起：owner 提出「角色主動推薦附近好吃好玩」的構想，討論中延伸出隱私／個人化兩難、
> 關鍵字回饋的顆粒度問題、以及「負向回饋輸入介面」的具體設計。
> 分類：**兩個正交子功能**——一個是新聞模組的小改良，一個是全新的輕量模組雛型。

## 0. 討論結論摘要（決策依據，之後不要重新爭論這幾點）

1. **不做「分析食記／喜好去推薦」**。理由不是技術難度，是定位：DeST 角色是陪伴向而非
   生活決策助手，個人資料分析＋地點推薦是外送／在地生活 App 在做的事，做了會讓角色
   人設變功利，也踩到「敏感資料不放第三方」的精神（食記＋喜好是相當私密的組合）。
2. **個人化的資料來源是「使用者自己維護的顯性關鍵字清單」**，不是系統偷偷觀察／推論。
   這跟 FB／YT 演算法的「一面倒」問題不是同一種病——那些平台用「停留時間」當興趣代理
   指標去優化，指標本身就會失真且隱性學習到你自己都不知道；DeST 現有的關鍵字組全部
   由使用者自己輸入／刪除，沒有這個回饋失控迴圈。
3. **也不能完全沒有調節（噗浪式）**。純顯性清單如果放著不管，會停在「你半年前的興趣」，
   跟朋友喜好自然發散一樣變得無聊。解法是**小比例的探索額度**（同類別但清單外的內容），
   不是自動學習，主動權仍在使用者手上決定要不要把新東西加進清單。
4. **關鍵字衝突（同一則內容同時命中正向與負向關鍵字，如「職業體育」沒興趣但「台灣選手
   國際奪牌」有興趣）不需要智慧判斷誰蓋過誰**——這是關鍵字系統的粒度問題，只要負向回饋
   綁定「使用者實際輸入的那個詞」而非籠統分類，兩個詞本來就是不同粒度，同時存在即可。
   規則訂為：**只要命中任一正向關鍵字就優先顯示，不做正負權重加總抵銷**，寧可多顯示、
   使用者可以再單獨對更精確的詞按不感興趣微調。
5. **負向回饋介面採結構化輸入，不經過 LLM 猜詞**：
   「我對 `[___]` 沒興趣，之後不要跟我講」，空格處使用者自己打字（或從推薦訊息預填），
   直接存成關鍵字，跳過「LLM 誤判自由文字意圖」這個風險（例如把「今天不想吃辣」誤判
   成永久討厭辣的東西）。

## 子功能 A：新聞模組改良——「不感興趣」快速輸入

### 現況（已有基礎設施，不用新增資料結構）

`NewsModuleSettings`（`src/core/news/types.ts`）已經有兩層負向機制：

| 機制 | 欄位 | 行為 | 現有 UI |
|---|---|---|---|
| **硬封鎖** | `blacklist: string[]` | 比對 title／summary／tags／category／source，命中就整則過濾掉（`filter.ts:192,329`） | 桌面＋手機設定頁皆可編輯標籤 |
| **軟衰減** | `feedback.adjustments: Record<sourceId, number>` | 對**既有來源**按讚倒讚微調權重，`-0.5`／次，下限 `-1.5`（`ipc.ts`、`settings.ts`） | 桌面新聞設定面板既有的按鈕（`SettingsPanel.tsx:991`） |

owner 想要的「以後不要跟我講 OO」是**永久、明確範圍的硬封鎖**，語意上對應 `blacklist`，
不是 `feedback.adjustments`（那個是對「已存在的來源」做軟性降權，不適合承接一句自由造句）。
**結論：不新增資料結構，直接復用 `blacklist`。**

### 新增：兩個輸入入口，都是「照樣造句」表單

```
我對 [___________] 沒興趣，之後不要跟我講
```

填入的文字**直接**當一筆 `blacklist` 項目存檔，不經過模型解讀。

1. **設定頁常駐入口**（新聞設定面板既有的黑名單區塊，只是換一句更口語的說明文案／
   或加一顆獨立按鈕彈出此表單，本體其實就是現有的黑名單標籤輸入框）。
2. **從推薦訊息直接觸發**（新增）：新聞訊息旁加一顆「不感興趣」快速鍵，點下去彈出同一個
   表單、**空格處預填該則新聞命中的關鍵字**（`NewsItem.keyword` 欄位已經存在，見
   `types.ts:189`，不需要另外跑模型抽詞——這則新聞本來就是靠某個 `NewsSource`
   關鍵字命中才被抽到的，資訊系統早就知道）。使用者可以直接確認，或改得更精確
   （例如把預填的「棒球」改成「職棒」，避免誤傷「台灣選手國際奪牌」這種你其實想看的）。

### 預定影響檔案（僅新增入口 UI，不動抽選邏輯）

- `src/renderer/src/modules/news/SettingsPanel.tsx`：黑名單區塊加照樣造句文案／獨立表單
- 訊息 UI（顯示新聞訊息的元件，需要找到目前「說點什麼」新聞訊息渲染處）：加「不感興趣」
  快速鍵，需要能拿到該則訊息對應的 `NewsItem.keyword`（若訊息 metadata 目前沒帶這欄位，
  需要補；先確認 `newsLink` 或類似欄位現況）
- 手機對應元件：`src/mobile/ui/news/NewsSettingsView.tsx` 及訊息渲染處同步
- **不動**：`core/news/filter.ts`、`core/news/keywordGroups.ts`（core 抽選邏輯本身完全不變）

### 不在本次範圍

- 自由文字輸入＋LLM 意圖萃取（已否決，見上方結論 5）
- `feedback.adjustments` 機制的改動（維持現狀，兩套機制正交共存）
- 正負關鍵字加總抵銷的判斷邏輯（已否決，見上方結論 4）

## 子功能 B：附近好吃好玩推薦（輕量版，新模組雛型）

### 定位

比照新聞陪聊的「主動推播」架構（角色在「說點什麼」或合適時機主動開口），**不做**：

- 不分析食記／使用者行為去猜喜好（見結論 1）
- 不做客製化排序演算法／推薦引擎
- 不做高頻率推播（避免變成通知轟炸，社交壓力來源之一）

### 架構草案（沿用新聞模組的關鍵字組機制）

跟新聞模組是**同一套「關鍵字組→內容」管線**，只是換一個資料來源：

```
興趣池 = 使用者自訂的地點類關鍵字（美食類型／店家類型／活動類型…）
       + 一小比例探索額度（同類別但清單外，製造驚喜、避免同溫層固化）
  ↓
打外部地點 API（Google Places 或同等服務，待 owner 決定，見下方開放問題）
  ↓
角色主動提起（沿用「說點什麼」既有的主動發話判斷時機，不另外設計新的觸發規則）
  ↓
訊息旁「不感興趣」快速鍵 → 照樣造句表單（與子功能 A 同一套 UI 元件／同一套 blacklist 概念，
                                          只是這個模組自己的黑名單清單，不跟新聞共用）
```

是否要做成**新聞模組底下的一個來源類型**（類似現有 `NewsSourceType: 'keyword'|'rss'|'json'`
多加一種），還是**獨立新模組**（有自己的 `ModuleSettingsEnvelope`），架構上兩條路都通，
但獨立模組比較乾淨——地點推薦跟「新聞」在語意上是不同領域，硬塞進新聞模組的
`keywordGroups`／`blacklist` 會讓那份設定檔混雜兩種不相關的東西，日後維護與匯出/匯入
（DST pack、ST 卡相容性）也會变得混亂。**建議獨立模組**，但沿用新聞模組已驗證過的
「關鍵字組＋黑名單＋主動發話時機判斷」這一整套設計模式（不是複製程式碼，是複製架構）。

### 開放問題（需要 owner 決定才能排進 `TODO.md` 開工）

1. **外部 API 選哪家**：Google Places API 需要金鑰＋可能有費用（比照現有天氣模組
   CWA API Key 走使用者自填的模式，但 Google Places 的免費額度／計費規則要先確認）；
   是否有無金鑰／免費的替代方案（如 OpenStreetMap／Overpass API，資料完整度較低但零成本）？
2. **探索額度的比例與呈現方式**：例如「十則裡一則探索」是否合理？探索的內容要不要標示
   「這是嘗試推薦，不在你的清單裡」讓使用者知道差異，還是完全無痕融入？
3. **定位權限**：地點推薦勢必要拿使用者目前位置，桌面版原本沒有這個需求（天氣模組的
   GPS／IP 定位是給獨立版手機用的），桌面版角色要推薦「附近」是否需要额外處理
   （例如手動輸入城市而非抓 GPS）？
4. **獨立模組 vs 掛在新聞模組下**：上面建議獨立模組，但如果 owner 認為這功能用量低、
   不值得開一整條新模組的維護成本（設定頁、匯入匯出、模組開關），也可以先做成新聞模組
   底下的第四種來源類型，之後真的需要再拆分。

### 已否決／不做

- 分析食記推斷喜好（結論 1）
- 用停留時間／點擊率等隱性訊號做排序（結論 2，避免 FB／YT 那種失控迴圈）
- 正負關鍵字加總抵銷判斷（結論 4，沿用子功能 A 同一套規則）
- 自由文字＋LLM 意圖萃取當唯一輸入方式（結論 5）
