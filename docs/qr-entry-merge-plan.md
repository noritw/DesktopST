## 0. 一句話

現在「掃 QR」這件事在手機上有**兩個長得很像但能力不同的入口**、在電腦上有**一張永遠指向中繼的 QR**,
三者互相打架,結果是**使用者無法完成一件他明明該做得到的事**（把電腦的資料連同 API Key 帶到手機）。
這次把「先問用途、再給對應連線」變成明確的流程,取代目前「同一張 QR 到處掃、失敗了才知道」的設計。

## 1. 為什麼要做（owner 2026-08-24 實機經歷）

owner 換裝正式簽章版 APK 後要把資料匯回手機,照順序撞到三件事:

1. 從「關於 → 切換模式」掃 QR → 被擋:「這版本不支援中繼」
2. 以為是中繼的問題,把電腦端**中繼關掉** → 再掃 → **Server Error**

> 這不是文案不夠清楚的問題,是**流程本身把選擇題丟給了不具備判斷資訊的人**。

## 2. 現況：三個各自獨立的缺陷（已查證）

### 2.1 電腦端：QR 永遠指向中繼,關掉中繼也一樣 ← **這是 bug,不是設計**

`src/renderer/src/windows/QRCodeWindow.tsx:20`

```js
function pickUrl(s: MobileStatus): string | null {
  return s.relayUrl || (s.tunnelReady && s.url ? s.url : s.running ? s.localUrl : null)
}
```

`s.relayUrl` **永遠是非空字串**——`relayService.ts` 的 `getRelayUrl()` 不管中繼有沒有啟用、
有沒有連上,都無條件用設定檔組出一個網址:

```js
export function getRelayUrl(): string {
  const cfg = getConfig()
  return `${cfg.relayUrl}/${cfg.deviceId}?token=...`   // 永遠有值
}
```

所以 `||` 左邊永遠成立,**後面兩條路（tunnel 網址、區網網址）永遠走不到**。

後果:

| 中繼狀態 | QR 指向 | 結果 |
|---|---|---|
| 開啟 | 中繼 | 連得上,但電腦端判定「非區網直連」→ **金鑰不傳** |
| **關閉** | **仍是中繼**（`registerOffline()` 已告訴中繼「我離線了」）| 中繼回 **503** → 手機顯示 **Server Error** |

**已實測驗證**：關閉中繼後直接打該中繼網址,回 `HTTP 503`。

換句話說:**目前的程式碼下,使用者不可能讓 QR 顯示區網網址。**

### 2.2 手機端：兩個入口共用同一張 QR,但能力不同

**電腦端只有一張 QR**（`QRCodeWindow.tsx` 是唯一產生 QR 的地方,從「擴充 → 手機遠端對話／遙控」開啟）。
手機端有兩個地方會掃它,兩邊都呼叫同一支 `parsePairingUrl()`：

| 入口 | 位置 | 用途 | 支援中繼？ |
|---|---|---|---|
| **從電腦匯入**（`SyncImportView`）| 首頁選單,QR 圖示 | S1：把角色/設定/對話**複製一份**到手機 | ✅ 支援（且會嘗試自動升級成區網） |
| **切換模式**（`ModeSwitcher`）| 「關於」頁裡 | S2：切成遙控模式,**直接讀電腦那份**資料 | ❌ 不支援,硬性要求區網直連 |

兩者的差別對使用者來說其實是 **「複製一份過來」vs「直接讀電腦上那份」**,
但目前的文案完全沒把這件事講清楚,而且**錯誤訊息不指路**：

`ModeSwitcher.tsx:261`
```
'這條連線是透過中繼，這個版本還不支援用中繼建立即時遙控。請確認手機和電腦在同一個 Wi-Fi 再試一次'
```

這句話沒有告訴使用者「你可能根本走錯入口了,想複製資料請去首頁的『從電腦匯入』」。

### 2.3 自動升級區網的機制存在,但實測沒有生效 ← **需要在這次一併查清**

程式碼裡**已經有**「掃到中繼網址時自動改走區網」的機制,而且兩個入口都有:

- `syncImport.ts` 的 `upgradeToLan()`（S1 匯入用）
- `connection.ts` 的 `resolveLiveRemote()`（S2 切換模式用）

運作方式:電腦端在非直連時,於 `/api/sync-init` 回應裡附上 `lanUrl`
（`mobileServer.ts:1657` → `bridge.getLanBaseUrl()` → `http://<區網IP>:3721`）,
手機拿同一個權杖改連那個位址再問一次,通了才採用。設計本身是對的
（只接受 RFC1918 私有位址,金鑰給不給仍由電腦端依 `remoteAddress` 判定）。

**但 owner 實測時它沒有生效**——手機顯示的是「這條連線不會傳輸 API Key」,
代表 `upgradeToLan()` 回了 `null`。

已排除的可能:
- ✅ 手機 `192.168.50.104` 與電腦 `192.168.50.136` **確實在同一網段**（實測 `adb shell ip route`）
- ✅ 電腦端 `/api/sync-init` 從區網 IP 打進去**確實回傳 `lanDirect:true` 與完整金鑰**（實測 curl）
- ✅ `getLanBaseUrl()` 組出的位址格式正確,且 `isPrivateHost()` 會放行

**尚未查清**（動工第一件事）:為什麼手機那一趟升級失敗。可能方向:
- CapacitorHttp 的逾時／cleartext 行為（`getJson` 預設 30 秒,理論上夠）
- Wi-Fi AP isolation（部分路由器預設隔離無線用戶端,手機打不到電腦的區網 IP）
- 掃 QR 當下手機是否真的在該 Wi-Fi 上（而非行動網路）
- `upgradeToLan()` 的 `catch` 把真正的錯誤吃掉了,**沒有任何日誌**

> ⚠️ **這一條會直接影響設計取捨。** 如果自動升級其實可靠、只是偶發失敗,
> 那新設計可以繼續依賴它;如果它在常見環境下就會失敗（例如 AP isolation 很普遍）,
> 那「備份資料自動走區網」這個承諾就不能只靠它,要有明確的失敗提示與手動備案。
> **先查清楚再決定,不要直接照抄現有機制。**

### 2.4 「遙控不支援中繼」只對 APK 成立，網頁版一直都可以 ← **重要澄清**

> ⚠️ **這節是 2026-08-24 owner 質疑後查證補上的修正。**
> 初版本文件寫成「目前遙控明確不支援中繼」，owner 立刻反問「那我之前在外面
> 怎麼遙控的？」——**owner 是對的，那個說法過度概括了。**

差別在 **APK 原生殼 vs 網頁版**，不是「遙控」這個功能本身。

`src/mobile/ui/connection.ts` 的 `wsUrlFor()`：

```js
export function wsUrlFor(conn: Connection): string {
  if (window.__tunnelWsUrl) return window.__tunnelWsUrl   // ← 網頁版走這條
  // 後面是字串代換 http→ws，對中繼是錯的路由
}
```

`window.__tunnelWsUrl` 由**中繼的 Cloudflare Worker 在回傳 HTML 時注入**
（`src/main/cloudflare-worker.js:108`）。而且注入的位址**直接指向電腦的
cloudflared tunnel，繞過中繼**——換句話說 WebSocket 從來不經過中繼代理，
中繼只代理 HTTP。

| 連線方式 | WebSocket 位址哪來 | 遙控 |
|---|---|---|
| 手機瀏覽器掃 QR 開網頁 | Worker 注入 `__tunnelWsUrl`，直指電腦 tunnel | ✅ **一直都可用**（owner 在外面用的就是這條）|
| APK 原生殼切換到遙控模式 | 頁面是本地載入的、沒經過 Worker → `__tunnelWsUrl` undefined → 落到字串代換 | ❌ 卡在「連線中斷」 |

**所以 `ModeSwitcher.tsx:261` 那句擋人的訊息，語意上也該修**——
它現在寫「這個版本還不支援用中繼建立即時遙控」，會讓用過網頁版的人困惑。

**修法方向（預估小改，但未驗證）**：APK 缺的只是「知道電腦的 tunnel 網址」。
那個位址電腦自己就有（`getCloudflaredUrl()`），現成的 `GET /api/connection-info`
（`mobileServer.ts:1857`，目前只回一個 `lanDirect`）加一個欄位回傳它，
再讓 `wsUrlFor()` 在原生殼下優先採用，就能讓 APK 也走通同一條路——
**不需要做「WebSocket 經中繼代理」那種大工程。**

⚠️ 待驗證的點：tunnel 網址會隨 cloudflared 重啟而變（trycloudflare 的免費網址是動態的），
所以不能只在配對時拿一次就存著，要在每次建立連線前重新問。

## 3. owner 指定的方向（2026-08-24）

原話:

> 我覺得手機和電腦兩邊都要各自合併入口,手機端先問使用者要做什麼（從電腦複製資料／直接遙控電腦和電腦同步）
> 再掃 QRCode,電腦端產出 QRCode 的出口可能也要改到「關於」那邊,先問使用者要做什麼,再出對應的 QRCode,
> 可能還要加上說明（備份資料就自動走區網,遙控就自動走中繼）

拆解成三條要求:

1. **手機端合併入口**：先問用途（複製資料／遙控同步）,再掃 QR
2. **電腦端合併出口**：先問用途,再出對應的 QR
3. **用途決定連線方式**：備份資料 → 自動走區網;遙控 → 自動走中繼

> ✅ 第 2 點的「改到『關於』那邊」owner 已於 2026-08-24 澄清：指**電腦端**的 QR
> 入口要從「擴充」搬到「關於」，且「要不要開放遙控」的設定一併整併過去（見 Q1）。
>
> ⚠️ 第 3 點「遙控就自動走中繼」**不是誤解**——網頁版經中繼的遙控一直都能用，
> 走不通的只有 APK 原生殼。詳見 §2.4。

## 4. 建議設計

### 4.1 核心概念：用途決定連線,不要讓使用者選連線

目前的模型是「**一張萬用 QR + 兩個能力不同的入口**」,使用者必須自己搞懂
中繼／區網的差別才知道該去哪掃。新模型反過來:

```
使用者只回答一個問題：「你想做什麼？」
       │
       ├─ 把電腦的資料複製過來 ──→ 需要區網直連（才有 API Key）──→ 出區網 QR
       │                              連不上時 → 明確說明為什麼、怎麼辦
       │
       └─ 遙控／即時同步電腦 ────→ 優先區網（功能完整）
                                    區網不通才退中繼（APK 目前走不通，修法見 §2.4）
```

**「中繼」「區網」這兩個詞不應該出現在主要流程裡**,只在失敗說明與進階設定裡出現。

### 4.2 電腦端

**入口位置改變**（owner 2026-08-24 指定）：從「擴充 → 手機遠端對話／遙控」
搬到**「關於」**，並把「要不要開放遙控」的設定一併整併進同一個地方。

`QRCodeWindow` 從「直接顯示一張 QR」改成「先選用途 → 顯示對應 QR」。

| 選項 | QR 指向 | 說明文字（給使用者看） |
|---|---|---|
| **把資料複製到手機** | **區網位址**（`localUrl`） | 「需要手機和這台電腦連同一個 Wi-Fi。API Key 只會在這種連線下傳送。」 |
| **用手機遙控這台電腦** | 區網優先,必要時中繼 | 「同一個 Wi-Fi 時速度最快;不在同一個網路時會透過中繼連線。」 |

**必修**：`pickUrl()` 的 `s.relayUrl ||` 短路要拿掉,改成依用途選址。
順帶要處理 `relayUrl` 永遠有值這件事——建議讓 `getMobileStatus()` 在中繼未啟用／未連上時
回空字串,而不是無條件組出網址（否則任何依賴 `relayUrl` 真值判斷的地方都會重蹈覆轍）。

### 4.3 手機端

**入口位置**（owner 2026-08-24 指定）：合併後的「連接電腦」流程放在**「關於」頁**，
`MainMenu.tsx` 首頁選單的 `sync-import` 項目**整個移除**。

兩個入口合併成一個「連接電腦」流程,先問用途:

```
┌─ 連接電腦 ─────────────────────┐
│                                │
│  [把電腦的資料複製過來]         │
│   角色、設定、對話複製一份到這支手機 │
│   手機之後可以獨立使用           │
│                                │
│  [遙控／同步電腦]               │
│   直接使用電腦上的資料           │
│   兩邊會保持同步                │
│                                │
└────────────────────────────────┘
              ↓ 選完才掃 QR
```

- 選「複製資料」→ 走現有 `SyncImportView` 流程
- 選「遙控／同步」→ 走現有 `ModeSwitcher` 流程
- **掃到「用途不符」的 QR 時,不要只報錯,要指路**
  （例如遙控流程掃到只能匯入的 QR → 「這張 QR 是給『複製資料』用的,要改成那個嗎？」+ 直接跳過去的按鈕）

舊入口一律移除（見 Q2），不留捷徑。

### 4.4 失敗時的說明必須具體

現在的失敗訊息只說「連不上」「不支援中繼」,使用者無從判斷下一步。
新流程的失敗訊息至少要能區分:

| 情況 | 該說什麼 |
|---|---|
| 手機不在同一個 Wi-Fi | 「手機目前不在電腦的網路上。請連到跟電腦同一個 Wi-Fi。」 |
| 同網段但打不到（疑似 AP isolation）| 「連得到網路但找不到電腦,可能是路由器的『用戶端隔離』擋住了。」+ 說明怎麼查 |
| 電腦沒開 / DeST 沒執行 | 維持現有訊息 |
| 走錯入口 | **指路到正確入口**（見 4.3） |

## 7. 已知風險

- **`relayUrl` 永遠有值**這件事可能不只影響 QR。動工時要 grep 一遍所有讀 `relayUrl` 的地方,
  確認沒有其他地方也在用「有沒有值」判斷中繼狀態。
- **AP isolation 無法從程式端解決**。如果 §2.3 查出來是這個原因,
  「備份資料自動走區網」這個承諾就無法在所有環境成立,設計要接受這個現實
  （例如提供「手動輸入電腦網址」的備案,或允許使用者知情下用中繼匯入但金鑰另外手動填）。
- **改 QR 選址會影響既有使用者**：已經配對過的手機記著舊網址（`readRememberedRemote`）,
  改動後要確認舊記錄仍能運作或被正確汰換。
- 這次改動橫跨桌面 renderer、mobile UI、main 三層,**`npm run typecheck` 與 `npm test` 都要跑**。

## 9. 落地筆記（2026-08-24，實作完成）

**§2.3 的真正根因不是 AP isolation**，而是 `src/main/index.ts` 的 `getLocalIp()`
從 `os.networkInterfaces()` 拿「第一個非內部 IPv4」——這台電腦裝了 Tailscale，
它的虛擬網卡（100.64.0.0/10 CGNAT，實測 `100.86.50.84`）排在真正的 Wi-Fi 網卡
（`192.168.50.136`）**前面**（用 `node -e "os.networkInterfaces()"` 直接確認順序）。
QR 上的「區網位址」因此變成 Tailscale 位址，`isPrivateHost()` 判它不是 RFC1918
私有位址就直接拒絕升級，**連網路請求都沒發生**。用 `adb shell` 對電腦 3721 port
直接發 raw TCP 請求驗證過區網連線本身完全正常（回 401，不是連不到）；
`AndroidManifest.xml` 也早有 `usesCleartextTraffic="true"`，cleartext 不是問題。
修法：新增 `isRfc1918()`，`getLocalIp()` 優先挑 RFC1918 位址。這個坑會咬到
任何裝了 Tailscale／其他 VPN 的使用者，不是這台機器獨有。

**階段一其餘部分**：`pickUrl()` 短路 bug 照 §2.1 修掉，改成 `getMobileStatus()`
在中繼未啟用／未連上時就把 `relayUrl` 回傳空字串（`s.mobile?.useTunnel !== false
&& tunnelReady` 兩個條件都要成立）。

**階段二**：`QRCodeWindow.tsx` 改成先選用途（`Purpose = 'backup' | 'remote'`）
才出 QR；「複製資料」用 `pickBackupUrl()`（純區網，不碰 relay/tunnel），
「遙控同步」用 `pickRemoteUrl()`（沿用原本 relay→tunnel→區網順位，現在
`relayUrl` 已經可信）。電腦端入口搬到「關於」頁的新「連接手機」卡片
（啟用開關＋開 QR 按鈕＋「進階遙控設定」連去隱藏的「遙控」分頁）；「擴充」
分頁與「遙控」分頁裡原本重複的「開啟 QR Code 視窗」按鈕都拿掉。手機端
`MainMenu.tsx` 的 `sync-import` 項目整個移除；`ModeSwitcher.tsx`（掛在「關於」
頁）本機模式下新增「連接電腦」區塊，兩顆按鈕分別轉場到 `SyncImportView`
（push('sync-import')）或展開既有的掃 QR／手動貼上區塊（`setShowPair(true)`），
取代原本「本機模式無條件顯示掃 QR」的邏輯。

**§4.3「走錯入口指路」沒做嚴格版**：評估後兩張 QR 本質上是同一個
`baseUrl+token`，只是位址挑選與金鑰判定不同，既有訊息（S1 的「這條連線不會
傳輸 API Key」、S2 連不上時的訊息）已經覆蓋大部分「走錯」情境，沒有另外做
偵測 QR 用途並強制跳轉的邏輯——如果 owner 真機測試後仍覺得容易走錯，屆時
再針對實際碰到的情境補。

**§2.4 APK 遙控中繼支援**：新增 `getTunnelWsUrl()`（`src/main/index.ts`，
讀 `getCloudflaredUrl()` 轉 `ws(s)://`），經 `mobileServer.ts` 的
`/api/connection-info`／`/api/sync-init` 回給手機；`connection.ts` 的
`resolveLiveRemote()`（配對當下）與 `probeRemote()`（之後每次 attach）都會
帶回它，`wsUrlFor()` 在沒有網頁版才有的 `window.__tunnelWsUrl` 時改用
`conn.tunnelWsUrl`。⚠️ **故意不寫進 `ModePref`**——trycloudflare 免費網址會變，
`App.tsx` 的 attach effect 每次都用 `probeRemote()` 現問一次，`Connection`
介面因此新增了 `tunnelWsUrl?: string` 這個不落地的欄位。`ModeSwitcher.tsx:261`
原本「這個版本還不支援用中繼建立即時遙控」的誤導訊息也改寫成不概括整個功能。
