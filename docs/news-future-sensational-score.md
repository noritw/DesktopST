# 新聞模組 — 標題主觀／情緒評分

> 狀態：**已實作（輔助模型輕量評分、只記錄不篩選版本）。** 規格外功能。
> 完成日：2026-06-07。owner 決定門檻值等參數先不開放使用者調整（避免增加理解負擔），
> 直接記錄到 LogWindow 的新聞 debug 面板供觀察，不參與篩選、不影響角色語氣。
> 提出日：2026-06-07（owner + AI 討論）。相關：`src/main/modules/news/filter.ts`、`docs/news-module-design.md`。
>
> **討論過程中方向有調整**：一開始設想的是「內容農場式聳動標題」，
> 但 owner 指出這類標題最近其實已經比較少見；真正比較常見、也比較難處理的，
> 是**各家媒體立場不同造成的下標偏頗**（用詞選擇本身帶主觀判斷或情緒），
> 因此本文件的評分對象從「聳動度」調整為「主觀／情緒程度」，方法上也從純規則式
> 轉向「規則式做不到，那要不要送 LLM 判斷」的討論（見下方「規則式 vs LLM 判斷」一節）。
> **目前 owner 決定先試的方案是文末的「輔助模型輕量評分、只記錄不篩選」。**

## 動機

新聞陪聊模組上線後，owner 觀察到一個潛在風險：部分媒體下標會帶有立場色彩或情緒化用詞，
角色若照單全收地評論，可能讓使用者誤以為「角色認同某個立場」，
長期下來甚至有被單一風格新聞「餵養」出特定傾向的疑慮（owner 表示目前實際出現頻率不算高，但值得先想清楚因應方式）。

之前嘗試過在 prompt 裡直接加「這標題可能誇大、請保持懷疑」之類的提醒語句，
但效果是讓角色的回話**失去個性、變得很「通用 AI 」**（見 `docs/news-future-keyword-groups.md` 同類教訓：
角色口吻不該被外部規則壓平）。

因此這次構想刻意**不碰 prompt / 角色語氣**，改從**抽選階段**下手——
讓進入候選池的新聞本身就比較不極端，角色仍用自己的個性去詮釋看到的內容。

## 標題主觀／情緒判斷：規則式 vs LLM 判斷

「聳動度」（誇張詞、感嘆號）和「主觀／立場偏頗」其實是兩個難度不同的問題：

- **規則式 / 字典比對**（比照 `detectLang` / `SIMPLIFIED_MARKERS`，`filter.ts:9-26`）
  能抓到「情緒強度」（誇張詞、感嘆號密度），但抓不到「立場方向」。
  政治偏頗往往體現在**用詞選擇本身**（同一件事，一邊說「改革」一邊說「強推」；
  或哪一方的說法被放在標題前面），這是語境判斷，字典規則涵蓋不到。
  更諷刺的是：若真要編一份「哪些詞算偏頗」的字典，編製過程本身就已經是一種立場判斷，
  反而引入新的偏見來源。
- **送 LLM 判斷**：較有機會抓出語境層級的主觀框架（"這句話預設了某個立場 / 用了帶價值判斷的形容詞"），
  但代價是：①每次抽選多一次模型呼叫（延遲、token 成本）；②**判斷的 LLM 自己也有傾向**——
  只是把「誰的標準算中立」這個問題從詞典轉移到模型的訓練資料上，沒有真正解決，只是換了一個不透明的黑盒。

**結論**：規則式只適合做「情緒強度」這種表層、可量化的指標；
「是否帶立場」這種語境判斷規則式做不到，若要做只能交給 LLM——但要小心別讓判斷本身的呼叫
和黑盒問題反而增加系統的不透明度。

## 已實作方案：輔助模型輕量評分、只記錄不篩選

權衡「LLM 判斷較準但有成本與黑盒疑慮」之後，採用的折衷方案：

- **只對「已經抽中」的那一則**（而非全部候選池）送一次輕量分類請求給
  新聞模組既有的「輔助模型」（`replyModel: 輔助`，現成架構，不必新增供應商串接）。
- 提問形式：「這句新聞標題的用詞是否帶主觀評價或情緒化色彩？請給 0~5 分並簡述理由」。
- **結果只記錄到 LogWindow 的新聞 debug 面板，不拿來做篩選依據**：
  - 不影響候選池組成 → 不會把「另一個模型的偏見」疊加到抽選邏輯上
  - 讓 owner 之後回頭看「最近角色聊到的新聞標題，主觀／情緒分佈大概如何」，
    用人的判斷力去觀察趨勢，而不是讓系統自動下結論
  - 之後如果觀察到真的有需要，再考慮要不要把分數拿來做進一步調整（如軟性權重）

**為什麼這個方案優於直接拿來篩選**：
- 成本最低——只多一次呼叫
- 避免「用一個黑盒的判斷去過濾另一個黑盒的輸出」這種疊加不確定性的設計
- 符合 owner 一貫的偏好：先觀察、再決定要不要做更進一步的自動化

### 實際落點

- `src/main/llm/promptUtils.ts`：`buildNewsSubjectivityClassifierSystemPrompt()`——
  極簡 system prompt，要求模型輸出 `<0~5 分>|<20 字內繁中理由>` 一行，不輸出其他內容。
- `src/main/llm/index.ts`：`classifyNewsSubjectivityWithLLM()`——
  仿照既有 `classifyEmotionWithLLM` 的寫法（同樣呼叫 `applyUtilitySettings` 走輔助模型，
  各 provider 分支直接呼叫 SDK），用正則 `^([0-5])\s*[|｜]\s*(.*)$` 解析回應；
  解析失敗或請求出錯一律回 `null`（呼叫端視為「沒有分數」，不會中斷主流程）。
- `src/main/ipcHandlers.ts`：在 `forceSpeakDirect`（一般「說點什麼」路線）與
  `triggerReminderSpeak`（提醒發話路線）兩處組 `NewsDebugInfo` 時，
  若選中的是真正抽到的新聞（非主題模式延續），就 `await` 呼叫一次分類，
  把 `score` / `reason` 併入 `item.subjectivityScore` / `item.subjectivityReason`。
- 型別：`NewsDebugInfo.item` 新增 `subjectivityScore?: number` / `subjectivityReason?: string`
  （`src/main/types.ts`、renderer 端 `src/renderer/src/types/index.ts` 同步更新）。
- UI：`LogWindow.tsx` 的 `NewsDebugPanel` 在「選中新聞」卡片上多顯示一行
  「主觀／情緒：N/5（理由）」，hover 有提示文字說明這只是觀察用、不影響抽選與角色語氣。
- 門檻值／是否啟用**沒有**做成設定項，維持「模組啟用就一律記錄」，避免使用者要理解額外參數。

### 怎麼測試

這個功能完全不影響角色回話內容或語氣，唯一可觀察的地方是 **LogWindow 的新聞 debug 面板**：

1. 確保新聞模組已啟用，且設定了至少一個來源（關鍵字 / RSS / JSON 皆可）。
2. 觸發一次新聞發話：
   - 最快：對某角色按「說點什麼」（若 `speakButton` 設為 `sometimes`，約 45% 機率才會抓新聞，
     建議先把它調成「每次」`always` 方便測試）；或
   - 觸發一個「啟用 `injectNews`」的提醒，等排程觸發。
3. 等角色回話完成後，打開 LogWindow → 找到**最新一則**有新聞發話的角色訊息 → 展開 prompt 檢視 → 切到「新聞」分頁。
   ⚠️ **注意**：`fileStore.pruneConversationDebugPrompts`（[fileStore.ts:664](../src/main/fileStore.ts#L664)）只保留
   **最近一則**新聞發話的 `newsDebug`，較舊訊息存檔時會整個被剪掉、連「新聞」分頁都不會出現
   （這是既有設計，不是這次新增功能造成的）。所以一定要看當前對話裡**最新**那則新聞發話，
   不要拿舊訊息來確認，否則會誤以為功能沒生效。
4. 在「選中新聞」卡片裡應該會看到新增的「主觀／情緒：N/5（理由）」一行
   （如果輔助模型分類失敗或回應格式不如預期，這行就不會出現——這是設計上的容錯行為，
   不會跳錯誤訊息或卡住角色回話）。
5. 可以手動找幾則「標題明顯帶情緒字眼」vs「中性陳述」的新聞來源做對照，
   觀察分數高低是否大致符合直覺；如果普遍不準，可能要調整 system prompt 的措辭
   （`buildNewsSubjectivityClassifierSystemPrompt`），而不是調分數本身。

> 補充：分類呼叫使用「輔助模型」（新聞設定 `replyModel` 之外、`AppSettings.llm` 的
> utility 分流設定），如果使用者沒有另外設定輔助模型，`applyUtilitySettings` 會直接沿用主模型，
> 行為等同照常呼叫一次主模型做分類——多一次呼叫但不影響功能正確性。

## 影響範圍評估（最終結果）

- 只動分類呼叫與 `NewsDebugInfo` 組裝，**完全不碰 `trigger.ts` 的 prompt 組裝**，角色語氣不受影響。
- 沒有新增 UI／設定欄位（owner 決定門檻值等參數先不開放調整，避免理解負擔）。
- 多一次輔助模型呼叫（僅在「真的抽到新聞」時觸發，主題模式延續話題不會重複評分）。
- 失敗容錯：分類請求或解析失敗時靜默回傳 `null`，LogWindow 該行就不顯示，不影響角色回話。

## 暫緩事項

以下屬於最初設想的規則式（聳動詞彙計分／軟性權重懲罰）方案，**目前暫緩、未實作**——
owner 認為內容農場式聳動標題已較少見，真正常碰到的是「立場用詞偏頗」這種規則式抓不到的問題，
因此改採輔助模型評分方案（已完成，見上）。如果之後觀察輔助模型評分覺得不夠用，
或想額外用便宜的規則式做「連抽防呆」，可以回頭參考本文件較早版本的構想（見 git 歷史）。
