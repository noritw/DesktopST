# 角色對使用者的印象（自動記憶）

> 狀態：**提案，未實作。** 規格外功能。
> 提出日：2026-08-03（owner 提出「要不要像一般 LLM 網頁介面那樣自動更新對使用者的記憶」）。
> 相關：`src/main/llm/summarizer.ts`、`src/main/fileStore.ts`、
> `docs/multi-device-platform-roadmap.md`（§3.1 手機版必做項會受影響）。
>
> **時機：不急。** 建議等 `core/` 抽乾淨後再做（理由見文末「什麼時候做」）。

---

## 1. 動機：現在缺的是哪一塊

DeST 已經有兩種「記憶」，但中間有個斷點：

| 現有機制 | 記什麼 | 範圍 | 誰維護 |
|---|---|---|---|
| `conv.summary`（自動摘要） | 這段對話發生過什麼 | **單一對話內** | 自動 ＋ 可手動編輯 |
| Persona preset | 使用者是誰 | 全域 | **只能手寫** |

缺口很具體：**在對話 A 自然講出來的事，換個角色或換個對話就沒了**，
除非使用者自己回頭去改 Persona。

所以本提案的價值不是「多一個記憶功能」，而是
**把「聊天中順口提到的事」接上「跨對話都記得」這條路**。

---

## 2. 定位：是「角色對你的印象」，不是「使用者記憶」

**刻意不照抄 ChatGPT 那套全域使用者記憶**，理由見 §6 風險。
語意上與 Persona 分工：

```
Persona（手寫、全域）        ＝ 我希望「每個角色」都知道的我
角色印象（自動、單一角色）    ＝ 「這個角色」從相處中認識的我
```

這樣切語意乾淨，不必發明新概念，也不會跟既有的 Persona 打架。

## 3. 資料模型（owner 2026-08-03 提出的兩個問題）

### 3.1 「同時跟好幾個角色聊，是不是每個角色都要一個欄位？」

**是每個角色一筆記錄，但不要加在角色卡上。**

不加欄位到 `Character` 的理由：會污染角色卡，且匯出時要多決定一件事
（DST 帶不帶？ST PNG 帶不帶？印象是私人資料，跟著角色卡外流並不妥）。

改為獨立存一份，比照 `pinned-notes.json` / `reminders.json` 的慣例：

```
%APPDATA%\DesktopST\impressions.json
```

**惰性建立**——只有真的聊過的組合才會有記錄。
桌上四個角色就最多四筆，每筆是一小段文字，量級與現行 `conv.summary` 相當，不會膨脹。

### 3.2 「中途切換使用者角色（Persona）怎麼辦？」

**這題比 3.1 尖銳，而且它是本提案的關鍵設計。** 換 Persona 等於換一個「我」。
若印象只綁角色，會出現：角色以 A 身分認識你、你換成 B 身分後，
角色仍拿 A 的事來跟你講。

> 📌 **這把鍵同時解掉了「TRPG 劇情被記成現實」的問題**——
> `ScenePreset.activePersonaId` 是必填，切情境必然切 Persona，
> 所以 TRPG 的印象天然存在另一把鍵底下。詳見 §6.1。

**結論：鍵用「角色 × Persona」兩個一起。**

```ts
interface UserImpression {
  characterId: string
  personaId: string
  text: string            // 濃縮後的印象內容（可手動編輯）
  updatedAt: number
  coversTs: number        // 已涵蓋到哪個時間點，比照 conv.summaryCoversTs
  sourceScenes?: string[] // 產生時所在的情境名稱（見 §6.2）
}

// 存檔結構：key = `${characterId}::${personaId}`
type ImpressionStore = Record<string, UserImpression>
```

行為：

- 用 A 身分跟小明聊 → 記在「小明 × A」
- 換成 B 身分 → 小明讀不到 A 那筆，等於重新認識你
- 換回 A → 之前的印象原封不動回來

**不會爆量**：惰性建立，四個角色 × 兩個 Persona 最多八筆，
沒聊過的組合根本不存在。

> 語意上也符合直覺：Persona 就是你正在扮演的「你」，換了人，關係當然分開算。

### 3.3 群組聊天

只有**實際回過話**的角色才更新自己的印象。
全部在場角色都更新的話，等於一次 N 次輔助模型呼叫，成本不划算，
而且沒發言的角色「學到東西」也不太合理。

---

## 4. 觸發與成本

**沿用現有自動摘要那套，不要再多一套排程。**

- 走**輔助模型**（`applyUtilitySettings`），比照 `summarizer.ts`
- 觸發時機比照 `memory.autoSummarizeAfter`：累積 N 則未涵蓋訊息才做一次增量更新
  （既有印象 ＋ 新訊息 → 新印象，手動編輯過的內容要保留語意，同摘要的作法）
- **節流是必要的**：owner 常態同時跟多個角色聊，
  若每個角色每輪都更新，成本會是現在自動摘要的數倍
- 指令用英文省 token，輸出繁中——比照新聞模組與摘要的既有慣例

## 5. 開關與編輯（**owner 明確要求，非選配**）

> Owner 2026-08-03：「不管是不是角色扮演，這功能都要可以給使用者手動開啟關閉、手動編輯內容。」

這也與專案既有的設計慣例一致：**所有會影響角色的東西，使用者都看得到、改得掉**
（摘要可編輯／可清除、訊息可「排除於記憶外」、提醒有管理視窗、
日曆設定有「目前讀到的內容」可當場驗證）。

自動記憶若是背景默默寫、沒有介面，它會是整個程式裡
**唯一一個看不見卻會影響角色的機制**——記錯了只會覺得「角色怪怪的」，
無從查起，而依 roadmap §2 目標 4，新手更不可能查。

必須有的：

1. **全域開關**（設定 → 記憶分頁，比照 `memory.autoSummarizeEnabled`）
2. **可看、可編、可刪的清單**，比照 Log 視窗現行的「記憶摘要」摺疊卡
3. **情境覆蓋**沿用既有機制（虛擬 module id，比照
   `desktopst.systemTime` 那套）——但**預設跟隨全域，不強制關閉**（見 §6.2）

**不做「寫入前先問使用者」**：那會變成每聊幾句就跳出來打斷，太吵。
折衷是靜默寫入 ＋ 明顯可見的清單，記錯了刪掉即可。

## 6. 風險

### 6.1 「劇情被記成現實」——**§3.2 的鍵已經在結構上解掉了**

> ⚠️ **本節初稿把這列為最大風險，那是高估。**
> Owner 2026-08-03 指出：「TRPG 的情況下理論上我的使用者身分也會切換啊。
> 我總不可能開 TRPG 還說『我是一個獨立遊戲開發者』吧，這樣本身就是破壞體驗了。」
> 查證後這個直覺有資料結構背書，而且比直覺更強——見下。

原本擔心的失效情境是：

> 使用者在 TRPG 裡說「我是流亡的精靈王，父母死於戰火」
> → 記成使用者事實 → 三天後日常閒聊，角色關心「你父母的事還好嗎」

**這不會發生。** `ScenePreset.activePersonaId` 是**必填欄位**
（`src/core/types.ts`）——**每個情境都綁定一個 Persona，切情境就一定會切 Persona**。

因此 TRPG 情境下記錄的印象，會寫進
「角色 × TRPG 那個 Persona」這把鍵；切回日常情境時讀的是另一把鍵，
**那筆從頭到尾讀不到**。§3.2 為了「換身分」設計的鍵，順帶把這題也解了。

> 這也是為什麼 §7 排除了「只綁角色、不管 Persona」的作法——
> 那個版本才會有本節原本描述的問題。

**殘留的邊緣情況**（機率低，但不是零）：

1. 使用者把 TRPG 情境**指向與日常相同的 Persona**。
   這是使用者自己的設定，且既然是同一個 Persona，
   語意上他就是宣告「這兩個場合的我是同一個人」
2. **完全不使用情境功能**的使用者：只有一個 Persona，
   角色扮演與日常共用同一把鍵

兩者都靠 §5 的可編輯清單補救即可，不需要額外機制。

### 6.2 Owner 的決定：TRPG 情境**也保留**此功能

> Owner 2026-08-03：「我覺得 TRPG 角色扮演也可以留這個功能。」

依此，情境覆蓋**不預設關閉**，維持跟隨全域，由使用者自行決定。
搭配 §6.1 的結論，這個決定沒有額外風險——
TRPG 的印象本來就會存在它自己的 Persona 底下，不會污染日常。

仍建議保留一個很便宜的欄位：

> **每筆印象記下它是在哪個情境、什麼時候產生的**（`sourceScenes` / `updatedAt`）。

這不再是為了防 TRPG 污染（那題已解），而是給 §6.1 那兩個殘留邊緣情況、
以及 §6.3 的一般性誤判當辨識依據——編輯清單上看得出每條的來歷，該刪的比較好認。
成本只是多存兩個欄位。

### 6.3 抽取準確度

只該記「使用者主動透露的、關於現實的事」，不記劇情設定、不記角色自己講的話。
這條靠 prompt 約束，**一定會有誤判** → §5 的可編輯清單是必要的補救管道，不是加分項。

### 6.4 別把角色口吻壓平

比照 `docs/news-future-keyword-groups.md` 與 CLAUDE.md 記載的教訓：
印象注入 prompt 時是**背景資訊**，不是行為指令。
不要寫成「你必須提起使用者的這些事」，那會讓角色變得像在查資料。

## 7. 已排除的做法

| 做法 | 為何不採用 |
|---|---|
| 全域共用一份「使用者記憶」（ChatGPT 模式） | 角色扮演的使用者在意「關係」。A 角色知道的事 B 角色無故也知道，違和感比忘記更糟 |
| 存進 `Character` 的欄位 | 污染角色卡；匯出時要多決定帶不帶，而印象屬私人資料，不該隨卡片外流 |
| 只綁角色、不管 Persona | 換 Persona 後角色仍拿舊身分的事來講（見 §3.2） |
| 寫入前逐次詢問使用者 | 太吵，會打斷對話節奏 |
| 另做一套觸發排程 | 已有自動摘要的觸發機制，再加一套只會讓行為更難預測 |

---

## 8. 什麼時候做

**不急，且建議排在 `core/` 抽乾淨之後。**

理由：這是一段**純邏輯 ＋ 儲存**的功能，正是 roadmap §4.1 所指
「若在兩地各自實作就會 drift」的典型。現在做，等於桌面寫一次、
手機版（B3/B4）再寫一次；等 `core/` 與儲存 adapter 就緒後做，一份就夠。

- ❌ 不要插進 B2（Capacitor ＋ adapter 介面）——那是架構工作，混進新功能會讓驗收失焦
- ✅ 適合的時機：B2 定完儲存 adapter 之後，或手機版主線告一段落時
- 若真要提早做，至少把抽取與合併邏輯直接寫在 `src/core/` 底下，別寫進 `main/`
