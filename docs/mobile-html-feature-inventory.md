## 0. 一句話

`mobile.html` 盤出 **64 個可辨識功能**：
**49 項獨立版必做**、**15 項遙控專屬（不搬進獨立模式）**。
四個決策議題 owner 已於 2026-08-04 全數定案，見 §3。

實際新增的工作量比「49 項」聽起來小很多 —— 因為其中一大塊（個人新聞報）
桌面與手機**已經共用同一份後端邏輯**，而聊天、角色、預設組這些也全部已在 `core/`。
**B3 主要是寫 UI，不是重寫邏輯**，這正是 B1／B2／B2.7 買到的東西。

但也有一個**先前沒被算進去的缺口**（§5.2）：`mobile.html` 的功能只是「遙控用的手機介面」，
獨立版還需要一整套**桌面版才有的設定 UI**。roadmap §4.8 已經提過，但這份清單讓它更具體。

## 1. 分類的意思（白話）

| 分類 | 意思 |
|---|---|
| ✅ **獨立版必做** | 手機獨立版一定要有。§3.0 的硬性基準涵蓋的範圍 |
| ❌ **遙控專屬（不搬到獨立模式）** | 只有「手機連著電腦」才成立的功能。手機自己一台做不到，也沒有意義。**但依 §4.6，它仍要留在 APK 裡當可選模組** —— 「不搬」指的是不進獨立模式的功能集，不是從 APK 刪掉 |
| ❓ **待 owner 決定** | 兩種做法都說得通，且會影響工作量或使用者體驗。集中列在 §3 |

「依賴」欄的三種寫法：

- **core 已有** —— B1／B2.7 已經搬進 `src/core/`，手機直接呼叫，不必重寫
- **需新抽** —— 目前還躺在 `src/main/`，B3（或 B4）要先搬進 core
- **平台能力** —— 需要 Capacitor 外掛或瀏覽器 API（相機、檔案、通知⋯⋯）

## 3. Owner 決議（2026-08-04，四題全數定案）

> 以下都已拍板，**B3 開工時照著做，不要重新討論**。
> 每題保留「當初的兩個選項」供理解為什麼這樣選。

### ① 角色管理的語意 → **「本次對話誰在場」，但同步時對應桌面角色**

（原選項 A＝在場角色／B＝沿用「桌面角色」語意）

**決議：採 A 的語意、但用 B 的資料對應。**

- 手機 UI 上叫「這次對話有誰在場」—— 手機沒有桌面，講「桌面角色」使用者看不懂
- 與電腦同步時，這份名單**直接對應桌面版的桌面角色清單**（同一組角色 id）
- **電腦端若缺位置資訊（手機加進來的角色沒有座標），由電腦端自行產生** ——
  桌面已有 `spreadDesktopCharacters` / `repairDesktopCharacterLayout`（`ipcHandlers.ts` 84–262 行，
  §4.4 明列「留在 `main/`」），正是為這件事準備的，不必新寫

> **為什麼這樣切**：位置是**桌面平台獨有的顯示狀態**，不是角色資料的一部分。
> 讓它留在桌面端自行補齊，手機就完全不必知道「座標」這個概念存在 ——
> 同步的資料只有「誰在場」，兩邊各自決定怎麼呈現。

### ② 截圖「加入對話」（H3）→ **算遙控模組，獨立模式不做**

（原選項：只當遙控／順手做手機自身截圖）

理由（owner）：一般手機截圖存進相簿就能從相簿選進對話，B1 的選圖已涵蓋。
→ **不需要 Capacitor 截圖外掛與螢幕權限**，這一項工作量為 0。

### ③ 獨立模式的事件更新 → **抽象成「事件來源」介面** ✅ **已實作（2026-08-04）**

> `src/core/events/` ＋ `src/mobile/events/`。**與下面這張草圖有一處刻意的差異**：
> 沒有 `onStateChange` 回呼，改成發一種 `state-invalidated` 事件。
> 這樣重連對帳只是「同一種事件的其中一個原因」，G6 完全關在遙控實作裡。
> 細節見 `CLAUDE.md` 的 B3 階段 0-② 條目。

（原選項 A＝抽象一層／B＝UI 內 if/else）

**決議：採 A。** 獨立模式接本機事件、遙控模式接 WebSocket，UI 元件完全不知道差別。

~~**B3 第一天就要把這層定下來**~~ → 已在 B3 開工前定完。落地形狀比照 §4.4b 的 adapter 慣例：

```
core 或 UI 層定義介面（onMessage / onThinking / onThinkingDone / onStateChange）
  ├─ 獨立模式實作：本機 core 直接發事件
  └─ 遙控模式實作：包住現行 WebSocket（含重連對帳、回前景重抓）
```

G6（重連對帳）因此**留在遙控那一支實作裡**，不會汙染獨立模式。

### ④ 編輯功能 → **全部進 B3**，且範圍比原本問的更大

（原選項：進 B3／延後到 B3.5）

**決議：進 B3。且不只情境／Persona／世界觀，「角色庫與角色卡的編輯」也一併進。**

Owner 原話的意思很明確：**手機版要能獨立運作，這些東西不能少。**
少了任何一項，「不需要電腦」這個前提就不成立 —— 那等於 §4.6 的定位沒有達成。

因此 B3 的範圍明確包含：

- 情境（Scene）／Persona／World 預設組的新增・編輯・刪除
- **角色庫管理 ＋ 角色卡編輯**（人格、開場白、圖片、之後的 Lorebook 條目）
- 角色卡匯入／匯出（PNG ＋ DST Pack；`core/card/` 已就緒）

> 這使 §5.2 那塊「桌面才有的設定 UI」正式成為 B3 的一等公民，**不是加分項**。

## 4. 盤點時發現的既有重複實作

### 隨機工具算了三次 —— ✅ **已解（2026-08-04）**

原始狀況：

| 位置 | 內容 |
|---|---|
| `src/renderer/src/utils/randomTools.ts` | 桌面版（`computeRandomResult` 等 9 個匯出） |
| `src/main/mobileServer.ts:169-205` | 伺服器端 |

**三份的機率表已經長歪了**，不是「同一份寫三次」而已：

| | 御神籤（大吉…大凶） | 擲筊（聖／笑／陰） |
|---|---|---|

同一支籤在桌面與手機的機率不同，而且**沒有任何錯誤訊息**

#### 搬完之後的配置

```
src/core/random/dice.ts          computeRandomResult / diceNotation
                                 / modifierString / keptRolls
                                 / sanitizePendingRandomTool
src/core/prompt/randomTokens.ts  makeTokenString / hasRandomTokens

```

- **以桌面版那份為準**，逐字沿用（`mobileServer` 與 `mobile.html` 的權重向它對齊）
- `renderer/utils/randomTools.ts` 改為轉出檔 ＋ 保留三支 **UI 文案**
  （`getToolEmoji` / `formatPendingLabel` / `formatResultBadgeText`）——
  依 §3.3 這些不得進 core
- token 字串放 `core/prompt/` 而非 `core/random/`：它們是**訊息內容**，
  適用 §3.3 的 prompt 例外條款，該條款要求這類字串集中在 `core/prompt/` 底下
- 籤詩等第、筊象、正反面等中文**留在 `core/random/`** —— 那些是
  `RandomResult` 的**資料值**（會存檔、會進 prompt），不是介面語言
- HTTP 端點的參數夾擠獨立成 `sanitizePendingRandomTool()`，
  在信任邊界呼叫；`computeRandomResult` 本身不夾，避免桌面與手機行為變得難以推理

**驗證**：以可重現的偽亂數讓新舊兩份實作吃同一串亂數，
`computeRandomResult` × 11 種參數 × 200 個 seed、`expandRandomTokens` × 8 段文字
× 200 個 seed，加上 token 產生與辨識 —— **3,819 項比對零差異**。

日後這塊的回歸交給 `pre-b3-work-assessment.md` §6.2 規劃的 vitest。）

#### ⚠️ 唯一的行為改變

`mobileServer` 與 `mobile.html` 的**御神籤與擲筊機率變了**（改成與桌面一致）。
`/api/random` 端點目前**零呼叫端**（`mobile.html` 早已改成前端自己算），

## 5. 回推：B3 的範圍與估時

### 5.1 結論

> **原估 4–8 週已不適用。加入 §3 決議 ④（預設組編輯 ＋ 角色庫／角色卡編輯）後，
> 合理範圍是 8–12 週。**
>
> ⚠️ **但 owner 2026-08-04 明示：時間不是限制條件**
> —— 這是興趣專案，「架構漂亮、程式好用、之後好維護」優先於交付速度。
> **所以下面的週數只是給接手者判斷「這件事有多大」用的，不是進度壓力。**
> 遇到「趕一點但會留技術債」與「慢一點但乾淨」的取捨，一律選後者。

原本 4–8 週的估計是把手機端設定 UI 想成「桌面版的簡化子集」。
決議 ④ 之後它不是子集了：**手機要能完整建立一個角色並開始聊天，等同桌面版的角色編輯器全套。**

### 5.2 為什麼清單「不大」但工作量沒變小

一個容易誤判的地方：這份清單只涵蓋**遙控介面**的功能。
`mobile.html` 是設計來「用手機操作電腦上的 DeST」的，所以它**天生缺一整塊**：

| `mobile.html` 有的 | `mobile.html` 沒有、但獨立版一定要有的 |
|---|---|
| 切換角色 | **建立／編輯角色**（人格、開場白、圖片、Lorebook⋯⋯）← 決議 ④ 已納入 |
| 切換情境／Persona／世界觀 | **編輯**這三種預設組 ← 決議 ④ 已納入 |
| 讀新聞報 | **設定**關鍵字、黑名單、來源、排程 |
| — | **填 API Key、選供應商與模型、endpoint** |
| — | 記憶參數、模組開關、提醒 CRUD |
| — | 角色卡匯入／匯出（PNG／DST Pack）|

桌面的 `SettingsWindow.tsx` 是 **2,992 行**，`CharacterEditor` 那些還沒算進去。
手機不必全搬（無桌寵、無遙控），但這塊**明顯大於**本清單的 49 項。

**這不是新發現** —— roadmap §4.8 已經寫了「這是 B3 裡最大的單一項目，接手時勿再低估」。
這份清單的貢獻是讓對比變得具體：**mobile.html 是 B3 的一小半，設定 UI 是一大半。**

### 5.3 三件「不先做會付兩次錢」的事（**與時間無關，與架構有關**）

Owner 既然以架構品質為優先，這三件就更該擺在最前面 —— 它們的共同點是
**晚做的成本不是「慢一點」，而是「要拆掉重寫」**：

1. **事件來源抽象（決議 ③）** —— 元件的資料流形狀。做到一半再抽，等於重寫所有聊天元件
2. **`StorageAdapter` 的呼叫端接上** —— B2.7 收尾明載「呼叫端仍是 0，要接上得先反轉
   `storageAdapter → fileStore` 的依賴方向，留給 B3」。這是實質工作、**不是 UI**，
   而且手機端一旦先寫了自己的存檔路徑，就回不去了（正是 §4.1 的 drift）
3. ~~**隨機工具搬進 core（§4）**~~ —— ✅ **已完成 2026-08-04**，見 §4

### 5.4 建議的 B3 內部順序

> 週數是相對份量的標示，不是排程承諾（見 §5.1）。

```
階段 0  地基（不含任何 UI）
        事件來源抽象 ＋ StorageAdapter 接上
        （隨機工具搬 core ✅ 已於 2026-08-04 提前完成）
階段 1  UI 骨架：sheet／主題／toast／安全區域（G1–G4）
階段 2  聊天主線：A ＋ B ＋ C ＋ D（邏輯全在 core，主要是寫 UI）
階段 3  角色庫 ＋ 角色卡編輯（決議 ④ 的最大單項；含 PNG／DST Pack 匯入匯出）
階段 4  設定 UI：API Key／模型／記憶／模組開關／提醒 CRUD
        —— 依 §2 目標 4，第一層只露出「填 API Key」，其餘收進進階區
階段 5  預設組編輯：情境／Persona／世界觀（E3–E5 的編輯側）

```

**階段 0 完成前不要寫任何聊天元件** —— 那是這份順序唯一的硬性約束，
其餘階段可依當下興趣調換（階段 6 尤其獨立）。

遙控（H1–H11）依 §4.6 是可選模組，**排在 B3 之後**（roadmap 已列為 B6，隨手機 UI 的 web build 一起搬）。

### ⚠️ H 區塊是「不能刪掉 `mobile.html`」的真正原因

計畫書階段 7 寫的是「`mobileServer` 改提供 `out/mobile/`，`mobile.html` 保留一個
版本週期再刪」。但 **H1–H11 排在 B6**，比整個 B3 還晚 ——
也就是說**就算階段 6 的新聞報做完，`mobile.html` 仍然刪不掉**，
因為遙控是它獨有的功能。

→ 實務結論：階段 7 的「切換」應該理解成**並存**（兩個入口），
而不是「換掉」。真正的取代要等 B6 遙控面板完成。
