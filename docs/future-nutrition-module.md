### 0.1 公開版定位：獨立可選 App，而非主流程功能

這個模組的定位是**個人化、可選、低耦合**：

- 預設**關閉**，不影響新手入門與主流程體驗。
- 不是 DeST 的必須功能，也不是一個「全民健康 App」的主打體驗。
- 目標是讓需要的人能在 DeST 裡直接記飲食、AI 估營養、比對 Google Health 消耗，
  而不是把使用者資料、健康風格、個人偏好硬塞進主應用的核心體驗。
- 公開版中應以**模組化能力**與**本機資料優先**呈現，避免依賴作者後端、雲端同步、
  或任何需要長期維運的健康平台。
- 這種功能屬於「工具模組」而非「平台能力」：它可用、可關、可移除、可替代，
  但不應成為新手的必經入口。

這一點非常重要：**它可以公開、可以開源、可以給人下載，
但它必須保持作為可選模組的定位。**

## 3. 產品形狀

### 3.1 獨立 App、獨立安裝包（2026-08-17 owner 改版決定）

> ⚠️ **這條推翻了原本「一 APK／一桌面程式、兩入口」的設計**（舊決議見下方
> 歷史記錄）。owner 2026-08-17 明確要求：**這個 App 的入口不要放在 DeST 裡面，
> 要另外開**——不是 DeST 底下可開關的一個模組，是使用者手機桌面／電腦上
> 看到的**另一個 App 圖示、另一個安裝包**。

- **手機**：獨立 APK，獨立 app id、獨立圖示，跟 DeST 的 APK 是两個各自安裝、
  各自更新的東西。不透過 DeST 的模組開關系統（`desktopst.*` module id 那一套
  不適用）。
- **桌面**：獨立的 Electron 執行檔／安裝包，不是 DeST 主程式底下的一個視窗或
  分頁。
- **可以共用的**：`core/` 底下的純邏輯（`core/nutrition/`：資料模型、關鍵字
  比對、TDEE、聚合計算）可以被兩個 App 一起 import——這是**同一個 git repo
  裡的另一個入口**，不是另開一個 repo。UI 層（手機的 Capacitor 殼、桌面的
  Electron 殼）則是全新的、獨立的。
- **不做**：DeST 裡面的模組開關列、飲食 icon 掛在 DeST 選單上、`PackageManager`
  停用元件那套「關掉聊天 launcher 只剩飲食」的設計——那整套是舊決議，
  跟這次的「另外開」互斥，**開工前務必先看 `docs/nutrition-module-kickoff.md`
  的最新版本，不要照這份文件底下舊的 3.1 段落遺跡做**（如果之後有人忘記
  刪乾淨的話）。

#### LLM 設定共用（owner 2026-08-17 決定：兩台裝置都裝 DeST 時共用它的設定）

- **桌面**：兩個程式是同一台電腦、同一個 Windows 使用者，飲食 App 可以直接
  **唯讀**存取 DeST 的 `%APPDATA%\DesktopST\settings.json` 取得供應商／模型／
  端點設定；API Key 走 `safeStorage`，同一台機器的同一個使用者帳號本來就解
  得開，可以比照讀取。**沒有裝 DeST 的電腦**：飲食 App 自己有一份獨立設定，
  使用者自己填供應商與金鑰。
- **手機**：⚠️ **Android 的 App 沙盒讓這件事沒有桌面那麼簡單**——兩個各自
  安裝的 APK **無法直接互相讀對方的儲存空間**，不像桌面同一顆硬碟同一個
  使用者那樣自然共用。務必做成**一次性匯入**，不是即時共用：飲食 App 第一次
  啟動（或設定頁裡）提供「從 DeST 匯入 LLM 設定」，做法比照角色卡／設定包
  匯出匯入（`dstPack.ts`／`.dstpack` 那套，或最簡單直接讓使用者手動輸入／
  掃 QR），**不要假設能像桌面一樣直接讀到對方的檔案**。匯入後兩邊是各自
  獨立的副本，之後誰改了設定不會自動反映到另一邊——這是誠實的技術限制，
  不是偷懶。**沒有裝 DeST 的手機**：飲食 App 自己有一份獨立設定。

### 3.2 極簡入帳

```
快覽／Widget → 快速入帳
  ├─ 關鍵字「三」→ 燻雞三明治／魚排三明治 → 點選代入（零 LLM）
  └─ 拍照（可選短註）→ 對庫命中則沿用；未命中才 LLM 估一次 → 入庫
```

硬規則：**庫內食物預設禁止 LLM 覆寫營養**（手編或明確「重新估價」才改）。

### 3.2b 每日飲食列表（MVP 主畫面之一）

進飲食入口後，**一顆按鈕**（或首頁主按鈕「今日紀錄」）打開全日列表頁——不是藏在設定裡。

**頁面內容**

| 區塊 | 內容 |
|---|---|
| 日期列 | 顯示目前日期；**上一頁／下一頁**切換不同曆日（無紀錄的日子顯示空列表＋合計 0） |
| 合計列（置頂或底部固定） | **今日總計熱量**、**今日總計蛋白質**（可並列相對上限／目標，超標紅字，與快覽同一套合計） |
| 餐次列表 | 每一筆：`時間`、`食物名稱`、`該筆熱量`、`該筆蛋白`（＝ FoodItem 每份 × 當次份量） |

**點食物名稱** → 進入該筆對應的 **`FoodItem` 詳情／編輯**（名稱、品牌、口味、營養、照片等）。  
同一 `foodItemId` 的多筆餐次**共用同一份食物資料**：在詳情改營養或名稱，之後所有引用該 id 的餐次顯示與合計一併跟著變（這正是「沿用同一份資料」的意義）。

列表列上另可提供次要操作（實作時）：改當次份量／時間、刪除該筆 `MealLog`——與「改食物主檔」分開，避免以為只改今天卻動到整庫。

**類似名稱怎麼辨別（是否顯示 ID／引用次數／上次食用）**

| 資訊 | 是否給使用者看 | 說明 |
|---|---|---|
| 內部 `foodItemId` | **預設不顯示**裸 UUID（難認、易誤導） | 進階／除錯可摺疊顯示短 id；日常靠下方欄位 |
| **品牌／店家／口味** | **列表副標必顯示**（有填才顯示） | 主辨識：「燻雞三明治 · 7-11 · 原味」vs「燻雞三明治 · 某咖啡 · 辣」 |
| **縮圖**（食物庫第 1 張） | 列表左側建議有 | 包裝類似時比文字更快 |
| **引用次數**（被幾筆 MealLog 使用） | **詳情頁＋關鍵字候選要顯示** | 「已記錄 12 次」→ 確認是常用那筆 |
| **上次食用時間** | **詳情頁＋關鍵字候選要顯示** | 「上次 昨天 12:30」 |
| 每份 kcal／蛋白 | 候選列與詳情顯示 | 同名不同熱量時一眼分開 |

資料上：`useCount`／`lastEatenAt` 可由 MealLog **聚合算出**（進 `core/`），不必強迫使用者手填；可選在 `FoodItem` 上快取並於入帳時更新以利排序。  
關鍵字候選與「今日列表」副標用同一套顯示規則，避免一邊分得出、一邊分不清。

若兩筆其實是不同食物卻曾誤绑同一 id：詳情提供「**另存為新食物**」（複製 FoodItem 新 id，可選是否把當筆 MealLog 改绑過去）。

### 3.3 角色邊界

- 可選注入極短 `[Food preferences]`（常吃／愛吃／忌口）
- **不**注入今日熱量／蛋白明細
- 飲食情境角色＝語氣／督促，不是帳簿 UI

### 3.3b 角色聊天素材：攝取／消耗差異（可選，預設關）

當 Health 讀取已開啟，且使用者允許讓飲食模組影響角色語氣時，
可把**近幾天的熱量攝取與消耗差異**轉成極短的角色上下文，而不是把每日帳本整段灌進 prompt。

這一層是為了讓角色能自然回應，而不是做健康診斷：

- **攝取 > 消耗連續幾天**：角色可說「最近吃得有點多」/「是不是最近有點放縱？」
- **攝取 ≈ 消耗**：不產生特殊語氣；不提醒、不加戲劇化
- **長期消耗 > 攝取**：角色可問「最近在減肥嗎？」/「最近是不是太累/太忙？」
- **極端偏差**：只在超過門檻時觸發，不連續噴發，避免角色變成健康顧問

採用規則：

- 只看**7 日移動平均**或**最近 3～7 天總和**，不看單日極端值
- 差異必須達到**明顯門檻**才進角色上下文（例如 ±10%～15% 以上）
- 若使用者最近體重/目標/活動量有明確設定，則可調整門檻與語氣
- 這部分**不會寫進帳簿 UI**，也不會在每次聊天都注入長串數字

設計目標：

- 角色感覺像「關心你」而不是「讀取健康報表」
- 只提供小範圍、低頻的情緒素材
- 不要做成「AI 健康顧問」或常駐診療系統

這項功能是**選配的角色對話補強**，與飲食帳戶本體分開。若使用者沒有開啟 Health 讀取，
或不願角色知道這些狀態，完全可關閉。

- 與角色主模型分開；熟食重複記帳趨近零 token

### 3.5 Health（選配，兩層，皆預設關）

> **owner 2026-08-18 決定：Health 讀排到 B9b（LLM 拍照估價）之前先做**（§6 分期表已更新）。

> 但體重／體脂／手錶當日消耗熱量目前完全沒有替代輸入方式，owner 自用天天要看，
> 優先度更高。寫入（Health 寫）維持原順序，不提前。

| 層 | 內容 | 優先度 |
|---|---|---|
| Health 讀 | 體重／體脂 → `BodyProfile`（體重機→Google→Health Connect，雲端資料直接同步，不必等使用者手動點「同步」）；手錶當日消耗熱量 → 動態調整 `dailyKcalLimit`（TDEE 靜態估算之外的即時修正，細節開工時再定） | **提前**：排在 B9b 之前 |
| Health 寫 | 本機確認後的營養 log → Health Connect／手錶 | 維持原順序（B9c，不提前） |

模組本體不依賴 Health。開源使用者本機完整可用。Client ID 自備（若雲端 API）。

## 4. 資料模型（草案）

儲存根（桌面）：`%APPDATA%\DesktopST\modules\desktopst.nutrition\`  
手機：對應 `StorageAdapter` key（與桌面 schema 相同）。

| 實體 | 要點 |
|---|---|
| `BodyProfile` | 身高、體重、年齡、活動量、算出的 TDEE 快取、**dailyKcalLimit**、**dailyProteinGoalG**（後兩者一等可編） |
| `FoodItem` | id、name、aliases[]、brand、store、flavor、perServing{kcal, proteinG, …}、photoKeys[1..3]、source、updatedAt；**可快取** `useCount`／`lastEatenAt`（或由 MealLog 聚合） |
| `MealLog` | id、foodItemId、servings、eatenAt、note?、photoKey?（當次可選） |
| 模組 settings | enabled、nutrition.llm、healthRead/Write flags、入口／widget 開關 |

照片：資料目錄內相對路徑／key，**不進 APK**；壓縮後存。  
聚合／TDEE／關鍵字對庫／報表：`core/` 純函式（可測、可注入 `now`）。

## 5. 換機、同步、匯出匯入、手動編輯

換手機是 owner 明確需求：**第一期必須能搬家**，不能等 S2／雲端。

### 5.1 三層能力（由易到完整）

| 層 | 時機 | 做什麼 |
|---|---|---|
| **N1 搬家包匯出／匯入** | 飲食模組 MVP 必做 | 單一檔帶走食物庫＋照片＋餐次＋身體檔＋模組設定（不含 API Key） |
| **N2 手動編輯／修檔** | MVP | UI 編 FoodItem／MealLog／上限；進階可匯出 JSON 用外部編輯器再匯入（校驗 schema） |
| **N3 接 S2 點對點** | B7 之後接線 | 桌面↔手機手動推送／拉取／合併＋差異預覽；與角色資料同一套同步宿主 |

不做：雲端後端、連上就自動同步（S3）。

### 5.2 搬家包格式（N1）

建議副檔名：`.destnutrition`（實作可為 zip）。

```
manifest.json          # schemaVersion、exportedAt、appVersion
body-profile.json
settings.json          # 剝除任何密鑰
food-items/*.json      # 一食物一檔或單檔陣列
meal-logs/*.json       # 可按月分檔以免過大
photos/<foodItemId>/01.webp …
```

規則：

- **API Key 永不進包**（與 DST Pack／§4.7 一致）
- 匯入前預覽：食物 N 筆、餐次 N 筆、照片體積、schema 版本
- 匯入策略（使用者選）：
  - **合併**（預設）：同 `id` → mtime／updatedAt 較新者勝；新 id 追加；衝突列表可點選
  - **僅補缺**：只加入本機沒有的 id
  - **覆蓋本機飲食資料**：危險操作，二次確認
- 舊手機匯出 → 傳檔（雲碟／纜線／電腦中轉）→ 新手機匯入，**不需兩機同時在線**

桌面與手機都要有匯出／匯入入口（換機常經電腦中轉）。

### 5.3 手動編輯（N2）

- 食物庫：改名、別名、品牌／店家／口味、營養數字、增刪照片（1～3）
- 餐次：改份量、時間、換绑 FoodItem、刪除
- BodyProfile／日上限／蛋白目標：隨時改
- 「匯出 JSON 片段／整庫」給進階使用者；匯入時 **schema 校驗**，失敗不寫入
- 不提供無校驗的任意檔案覆蓋（避免弄壞帳簿）

### 5.4 與 S2 對接（N3）

當 B7 就緒，把 nutrition 納入同步清單：

| 資料 | 合併規則（草案） |
|---|---|
| `MealLog` | 以 id **聯集**（append-only 為主）；同 id 取 updatedAt 較新 |
| `FoodItem` | 同 id 取較新；衝突進差異預覽（名稱／營養／照片數） |
| `BodyProfile` | 較新者勝；**dailyKcalLimit／protein 手改**優先於單純 TDEE 快取欄 |
| 照片 binary | 隨 FoodItem 走；缺圖則標記待補 |
| API Key／Health token | **永不同步** |

換機推薦路徑（有電腦時）：舊手機 → S2 推到桌面 → 新手機 S2 拉；  
無電腦或不想開同步：走 N1 搬家包即可。

### 5.5 遙控模式過渡

S2 未完成前：若手機以遙控連桌面，飲食資料可先以**電腦為唯一真本**（薄客戶端讀寫），與現有設定／新聞報模式一致。獨立模式則靠 N1 搬家包。
